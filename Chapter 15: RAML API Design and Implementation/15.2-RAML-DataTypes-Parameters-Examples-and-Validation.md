# 15.2 — RAML Data Types, Parameters, Examples, and Validation

## 1. Built-in types and constraints

RAML 1.0 types include `string`, `number`, `integer`, `boolean`, `date-only`, `datetime`, `object`, and arrays such as `string[]`.

```yaml
types:
  Customer:
    type: object
    additionalProperties: false
    properties:
      id: string
      name:
        type: string
        minLength: 1
        maxLength: 100
      age?:
        type: integer
        minimum: 0
        maximum: 120
      tags?: string[]
```

A property without `?` is required by default; `age?` is optional. Use constraints only when they reflect actual business rules. Runtime enforcement depends on the implementation and tooling.

## 2. Named types and composition

```yaml
types:
  Address:
    type: object
    properties:
      city: string
      country: string
  Customer:
    type: object
    properties:
      id: string
      name: string
      address: Address
  PreferredCustomer:
    type: Customer
    properties:
      loyaltyLevel:
        type: string
        enum: [silver, gold, platinum]
```

Use separate types when input and output shapes differ. For example, a create request may not include a server-generated ID or audit timestamps.

## 3. URI, query, and header parameters

```yaml
/customers/{customerId}:
  uriParameters:
    customerId:
      type: string
      minLength: 1
  get:
    headers:
      X-Correlation-ID?:
        type: string
    queryParameters:
      includeOrders?:
        type: boolean
        default: false
      limit?:
        type: integer
        minimum: 1
        maximum: 100
        default: 20
```

## 4. Enumerations and arrays

```yaml
types:
  OrderStatus:
    type: string
    enum: [NEW, ACCEPTED, SHIPPED, CANCELLED]
  OrderLine:
    type: object
    properties:
      sku: string
      quantity:
        type: integer
        minimum: 1
  CreateOrder:
    type: object
    properties:
      customerId: string
      items: OrderLine[]
```

An enum limits allowed values in the contract. Confirm the actual runtime rejects invalid values if that is a requirement.

## 5. Examples and named examples

```yaml
/orders/{orderId}:
  get:
    responses:
      200:
        body:
          application/json:
            type: Order
            examples:
              accepted:
                value:
                  orderId: o-1001
                  status: ACCEPTED
                  total: 149.99
              shipped:
                value:
                  orderId: o-1002
                  status: SHIPPED
                  total: 42.50
```

Check the parser and editor version used by your project, especially when using `example`, `examples`, or external `!include` files.

## 6. Consistent error types

```yaml
types:
  Error:
    type: object
    properties:
      code: string
      message: string
      correlationId?: string
      details?: object
```

Public errors should be actionable without exposing stack traces, tokens, database internals, or private hostnames. Keep error codes stable for clients.

## 7. Traits for shared method patterns

```yaml
traits:
  pageable:
    queryParameters:
      limit?:
        type: integer
        minimum: 1
        maximum: 100
      offset?:
        type: integer
        minimum: 0
  withCorrelationId:
    headers:
      X-Correlation-ID?:
        type: string
/books:
  get:
    is: [ pageable, withCorrelationId ]
```

Traits reduce repetition but should not hide important behavior.

## 8. Libraries and includes

Use `!include` to split content into files and `uses` to import a RAML library under a namespace. After refactoring, validate the main API entry point so all paths and references resolve.

## 9. Security declarations are not runtime enforcement

RAML can describe API-key/pass-through and OAuth security schemes. It does not provision an identity provider or automatically enforce policies. Never commit real secrets to the contract.

## Validation workflow

1. Parse the spec in your chosen RAML editor/tool.
2. Resolve all `!include` and `uses` references.
3. Review valid and invalid examples.
4. Try the design tool's mock feature if available.
5. Test the running Mule app with valid, malformed, and boundary-value inputs.
6. Confirm the implementation enforces constraints required by the business.

## Practice set

1. Define a Product with non-negative price and quantity and optional string tags.
2. Define separate `CreateProductRequest` and `Product` types.
3. Add a `sort` query parameter restricted to `name`, `price`, or `createdAt`.
4. Add named examples for successful and invalid orders.
5. Create and apply a correlation-ID trait.
6. Explain the difference between a type, trait, resource type, and library.
