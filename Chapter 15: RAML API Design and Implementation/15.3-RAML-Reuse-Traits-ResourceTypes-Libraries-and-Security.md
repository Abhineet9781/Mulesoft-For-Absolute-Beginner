# 15.3 — Reuse, Traits, Resource Types, Libraries, and Security

The goal of reuse is consistency and maintainability—not maximum abstraction. Always inspect the effective endpoint after applying reusable declarations.

## 1. Traits

Traits define reusable method-level behavior such as headers, query parameters, and responses.

```yaml
traits:
  pageable:
    queryParameters:
      limit?:
        type: integer
        minimum: 1
        maximum: 100
        default: 20
      offset?:
        type: integer
        minimum: 0
        default: 0
  hasRequestId:
    headers:
      X-Request-ID?:
        type: string
/books:
  get:
    is: [ pageable, hasRequestId ]
```

## 2. Resource types

Resource types describe reusable resource shapes, while traits describe method-level patterns.

```yaml
resourceTypes:
  collection:
    get:
      responses:
        200:
          body:
            application/json:
              type: <<itemType>>[]
    post:
      body:
        application/json:
          type: <<createType>>
      responses:
        201:
          body:
            application/json:
              type: <<itemType>>
/products:
  type:
    collection:
      itemType: Product
      createType: CreateProduct
```

Use this pattern only when it matches the actual endpoints. Avoid resource types that make a simple contract difficult to read.

## 3. Libraries and includes

A typical structure:

```text
api.raml
libraries/common.raml
types/product.raml
traits/pageable.raml
examples/product.json
```

A library fragment can contain reusable types:

```yaml
#%RAML 1.0 Library
types:
  Error:
    type: object
    properties:
      code: string
      message: string
```

Import it in the main API:

```yaml
#%RAML 1.0
title: Product API
uses:
  common: libraries/common.raml
/products:
  get:
    responses:
      500:
        body:
          application/json:
            type: common.Error
```

A library file must be a valid RAML library fragment. Keep relative paths correct and validate the complete API spec after moving declarations.

## 4. Security schemes

RAML can document security requirements, including OAuth 2.0 and pass-through/API-key patterns. The actual identity provider, token issuance, authorization, and enforcement belong to the real implementation and API management setup.

Illustrative OAuth configuration (placeholder host; not production-ready):

```yaml
securitySchemes:
  oauth:
    type: OAuth 2.0
    describedBy:
      headers:
        Authorization:
          type: string
    settings:
      accessTokenUri: https://identity.example.com/oauth/token
      authorizationGrants: [ client_credentials ]
securedBy: [ oauth ]
```

Verify scheme properties and supported grants against the RAML specification and the chosen tooling. Never include actual client secrets, tokens, or keys in source control.

## 5. Security design checklist

- Decide which operations are public and which require authentication.
- Distinguish authentication (who the caller is) from authorization (what they can access).
- Document required scopes/roles where appropriate.
- Enforce security through the gateway/runtime and identity provider.
- Apply record-level authorization where needed.
- Keep secrets outside the API specification.
- Avoid sensitive data in examples and logs.

## 6. Fragments, Exchange, overlays, and extensions

RAML supports reusable fragments, overlays, and extensions. Product support and workflows can vary by tool version. Use shared fragments or Exchange assets when ownership, versioning, and compatibility are clear. Review the effective contract after composition.

## Practice set

1. Apply pagination and correlation-ID traits to two endpoints.
2. Build a collection resource type and apply it to a resource.
3. Move Error into a library and import it with `uses`.
4. Mark the intended authentication requirements for each operation.
5. Explain why a RAML security declaration does not by itself secure a deployed API.
6. Refactor repetitive definitions and justify which ones are types, traits, or resource types.
