# 15.6 — RAML to Production: Governance, Versioning, and Troubleshooting

A reliable API requires more than a syntactically valid contract. This lesson covers compatibility, security, quality gates, operational readiness, interview questions, and a capstone.

## 1. Versioning and compatibility

Potentially breaking changes include:
- Removing or renaming a resource, method, field, or response.
- Changing a field's type incompatibly.
- Making an optional request field required.
- Removing a response status consumers rely on.
- Changing a field's meaning without changing its name.

Adding an optional response field may be additive, but consumers that reject unknown fields can still be affected. Evaluate real consumer behavior. A version label in RAML does not itself configure routing; runtime and gateway configuration must match.

## 2. Governance checklist

- Clear business purpose and identified consumers.
- Consistent resource naming, methods, status codes, and error formats.
- Useful descriptions and sanitized examples.
- Security documented and enforced by the appropriate runtime/gateway.
- Pagination, filtering, sorting, and rate limits defined where needed.
- Compatibility reviewed before publishing changes.
- Spec stored in version control.
- API ownership, lifecycle, and approval process defined.
- Specification and implementation tests run before deployment.

Available governance features depend on your Anypoint organization and subscription.

## 3. Contract-first CI/CD quality gates

A useful pipeline may:

1. Parse RAML with the team's agreed tool.
2. Resolve `!include`, `uses`, and fragment dependencies.
3. Check style and naming conventions.
4. Review contract diffs and compatibility.
5. Run mock/contract tests.
6. Build and test the Mule application.
7. Test runtime status codes, schemas, and security.
8. Publish approved artifacts.
9. Deploy through a controlled pipeline.
10. Monitor logs, metrics, alerts, and API analytics.

Keep credentials in a managed secret store, not in source files or pipeline logs. Pin tested tool versions.

## 4. Security and observability

- Never commit API keys, client secrets, bearer tokens, or private certificates.
- Use synthetic examples and placeholder hostnames.
- Distinguish authentication from authorization.
- Enforce access controls in the runtime/gateway/identity layer.
- Avoid exposing stack traces or backend details in public errors.
- Propagate a correlation ID across service boundaries.
- Log useful operational events without dumping sensitive payloads.
- Define service-level objectives and alerts as part of operational design.

## 5. Troubleshooting quick table

| Problem | First checks |
|---|---|
| Invalid document | RAML header, YAML indentation, required metadata |
| Type mismatch | Type definition, examples, request body |
| Include failure | Relative path and exact filename case |
| Unexpected route | Method, URI template, base path, selected spec |
| Unexpected 404 | Distinguish route-not-found from record-not-found |
| Mock/runtime mismatch | Mock examples are not a substitute for runtime tests |
| Contract/code drift | Automate contract and runtime tests |

## 6. Interview questions

1. What is RAML, and how is it different from YAML?
2. What does `#%RAML 1.0` identify?
3. When do you use URI parameters vs query parameters?
4. How are types, traits, resource types, and libraries different?
5. What are named examples useful for?
6. Does a RAML security scheme secure a deployed API automatically?
7. What does APIkit generate, and what must developers implement?
8. How do you test contract/runtime consistency?
9. Give examples of breaking and additive API changes.
10. Why can a mock pass while the actual Mule application fails?

## 7. Capstone — Product Catalog API

Design and implement these endpoints:

- `GET /products` with category, limit, and offset.
- `POST /products` with name, SKU, price, and quantity.
- `GET /products/{productId}`.
- `PATCH /products/{productId}`.
- `DELETE /products/{productId}`.

Requirements:
- Define Product, CreateProduct, and Error types.
- Add realistic examples and useful response statuses.
- Document authentication and authorization expectations.
- Use traits and resource types only where they improve clarity.
- Mock the contract, scaffold with APIkit, implement flows, and test valid and invalid requests.
- Document persistence, security, deployment, and monitoring choices.

### Acceptance checklist

- [ ] RAML and all fragments parse.
- [ ] Required/optional fields reflect actual rules.
- [ ] Success and error cases are documented.
- [ ] Examples match the types.
- [ ] No real secrets or sensitive data are committed.
- [ ] APIkit routes match the contract.
- [ ] Runtime tests verify status, headers, and body.
- [ ] Contract changes are reviewed for compatibility.
