# 15.4 — Hands-On: Design and Mock a Bookstore API

**Outcome:** Build a RAML contract for a Bookstore API and use mock behavior to review the contract before writing Mule business logic.

## 1. Create the project

Use Anypoint API Designer or Anypoint Code Builder to create a RAML 1.0 API specification named **Bookstore API**. UI steps can change between product versions, so consult the current official guide.

- [API Designer: design, mock, and publish API specs](https://docs.mulesoft.com/design-center/design-create-publish-api-specs)
- [Anypoint Code Builder API specs](https://docs.mulesoft.com/anypoint-code-builder/des-designing-api-specs)

## 2. Open the starter contract

Open [bookstore-api.raml](bookstore-api.raml) in this folder. Review the types, operations, responses, examples, traits, and placeholder security scheme. Validate it in your chosen RAML 1.0 parser/editor before using it.

It defines collection operations (`GET /books`, `POST /books`) and item operations (`GET`, `PATCH`, `DELETE /books/{bookId}`).

## 3. Review the design

Ask these questions before implementation:

- Are Book and NewBook distinct for a good reason?
- Is title uniqueness a business rule or merely an assumption?
- What should PATCH do with an empty body?
- Should delete return 204 with no body?
- How should an unknown or malformed ID be handled?
- Where will authentication and record-level authorization be enforced?
- What pagination/filtering conventions should be used?
- Are error responses consistent?

Record decisions in the contract rather than leaving them implicit.

## 4. Mock and test the contract

Use the editor's available mock/testing view:

1. Try `GET /books` and inspect the sample response.
2. Try `POST /books` with a valid NewBook example.
3. Try `GET /books/b-101`.
4. Review the documented 404 response.
5. Try a negative price or missing required property and see what the design-time validator/mock does.

**Mocking is not business implementation.** A mock may return sample responses without querying a database. Verify validation and behavior in the running Mule application as well.

## 5. Practice variations

- **Beginner:** Add an optional `author` query parameter to GET /books.
- **Intermediate:** Add category, sorting, and pagination with bounded values.
- **Advanced:** Move the Error type into a RAML library and add a reusable correlation-ID trait.
- **Stretch:** Add `POST /books/{bookId}/reviews` with a Review type and a 201 response.

## Completion checklist

- [ ] The RAML 1.0 file parses successfully.
- [ ] Required and optional properties are intentional.
- [ ] Examples match the declared types.
- [ ] Success and error responses are documented.
- [ ] Mocking has been tried with valid and invalid inputs.
- [ ] Security responsibilities are documented.
- [ ] No real secrets or sensitive data are included.
