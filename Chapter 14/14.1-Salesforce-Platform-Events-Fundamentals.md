# Chapter 14.1 — Salesforce Platform Events: Understand the Concept First

In this chapter, **Platform Events means Salesforce Platform Events**—Salesforce's event-based messaging feature. In a MuleSoft integration, Salesforce can publish an event and a Mule application can subscribe to it, or Mule can publish an event for Salesforce subscribers.

This is different from MuleSoft Anypoint MQ, JMS, and Mule runtime events. Those are related messaging concepts, but they are not the same product or API.

## 1. The easiest way to understand a platform event

Imagine a sales representative changes an Opportunity to **Closed Won**.

Instead of making Salesforce synchronously call five other systems, Salesforce publishes a business event:

> Opportunity_Won__e: Opportunity 006xx is won for account A100 and amount 25,000.

Subscribers can react independently:
- MuleSoft creates an order in an ERP.
- Another subscriber starts customer onboarding.
- A notification service alerts the account team.
- Analytics records the event.

~~~mermaid
flowchart TD
    A[Opportunity becomes Closed Won] --> B[Salesforce Flow or Apex publishes event]
    B --> E((Salesforce Event Bus))
    E --> M[MuleSoft subscriber]
    E --> N[Notification subscriber]
    E --> R[Reporting / analytics subscriber]
    M --> S[ERP / order system]
~~~

The publisher does not need to know every subscriber. This is a form of **publish/subscribe event-driven architecture**.

## 2. What exactly is a Platform Event?

A Platform Event is a custom Salesforce event definition. You define its fields, then publishers send event messages and subscribers receive them.

For example, create an event named **Order Ready** with API name Order_Ready__e.

Possible custom fields:
- Order_Number__c — Text
- Customer_Code__c — Text
- Order_Total__c — Number
- Status__c — Text

When an event is published, the message contains values for those fields. Platform Event messages are event records, not ordinary business records you edit like an Account. They are delivered through the event bus and are not queried as normal object records with SOQL.

## 3. Platform Events vs record changes

Do not confuse these two requirements:

**Requirement A: “Tell subscribers that an important business action happened.”**  
Use a Platform Event such as Order_Ready__e. You define the event and decide when to publish it.

**Requirement B: “Tell subscribers that an existing Salesforce record was created, updated, deleted, or undeleted.”**  
Consider Change Data Capture (CDC), which emits change events for supported Salesforce objects.

| Question | Platform Events | Change Data Capture (CDC) |
|---|---|---|
| What does it represent? | A business event you define | A change to a Salesforce record |
| Who decides to publish? | Your publisher logic: Flow, Apex, or API | Salesforce publishes changes for configured supported objects |
| Example | Order_Ready__e | Account updated |
| Payload | Fields defined on the event | Record-change information and changed fields/metadata |
| Good fit | Business milestones and cross-system signals | Record synchronization and change propagation |

A Platform Event is not automatically emitted just because any arbitrary record changes. Configure the publisher logic, or use CDC if the real requirement is record-change notification.

## 4. Important vocabulary

- **Publisher:** code, Salesforce Flow, or an external client that publishes an event.
- **Subscriber:** Apex, Salesforce Flow, or an external client such as Mule that listens for events.
- **Event bus:** Salesforce's event distribution infrastructure.
- **Channel:** the event stream a subscriber listens to; a custom Platform Event commonly uses a channel like /event/Order_Ready__e.
- **Replay ID:** an opaque position identifier used by supported streaming subscriptions for resuming within the retention window. Do not calculate or increment Replay IDs yourself.
- **Event UUID:** unique identifier associated with an event message in supported APIs.
- **Publish behavior:** determines the relationship between event publication and the publishing transaction, such as Publish After Commit.

## 5. Publish After Commit vs Publish Immediately

When the event announces data written by a Salesforce transaction, subscribers often need that committed data to exist before they process the event. **Publish After Commit** is the appropriate choice for that requirement: the event is published only after the publishing transaction commits successfully.

Use immediate publication only when its semantics fit the business requirement. An event can be published even if the surrounding transaction later rolls back, so a subscriber must not assume related data is already committed unless the design guarantees it.

## 6. Where MuleSoft fits

MuleSoft can:
- Subscribe to Salesforce Platform Events and process them in Mule flows.
- Transform the event payload with DataWeave.
- Call an ERP, database, HTTP API, or another connector.
- Publish Platform Events into Salesforce.
- Apply error handling, logging, correlation IDs, and controlled retry/replay strategies.

For new Platform Event and CDC integrations, review the Salesforce Pub/Sub Connector, which is based on Salesforce Pub/Sub API. The Salesforce Connector also provides event-streaming operations such as Replay Channel Listener; exact choices and features depend on connector/runtime versions and use case.

## 7. When Platform Events are a good fit

Use them when:
- A business milestone should notify several independent systems.
- A process should react to an event instead of polling Salesforce repeatedly.
- The publisher should not tightly couple itself to every downstream application.
- A near-real-time notification is needed and the event bus's delivery/retention semantics meet the requirement.

Do not assume the event bus is a permanent business database or an unlimited durable queue. Design for retention limits, subscriber outages, replay, duplicates, monitoring, and reconciliation.

## Quick memory rule

**Platform Event = “Something meaningful happened; interested subscribers should react.”**  
**CDC = “This Salesforce record changed; subscribers should learn about the change.”**
