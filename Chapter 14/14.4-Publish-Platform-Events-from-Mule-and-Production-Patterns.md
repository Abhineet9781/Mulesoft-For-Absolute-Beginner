# Chapter 14.4 — Publish Platform Events from Mule and Build a Reliable Integration

The previous lesson received events from Salesforce. This lesson covers the reverse direction and the production design questions that make an event integration dependable.

## 1. Two directions of integration

**Subscribe:** Salesforce publishes an event → Mule receives it → Mule calls downstream systems.

**Publish:** Mule processes an external change → Mule publishes a Salesforce Platform Event → Salesforce Flow, Apex, or another subscriber reacts.

~~~mermaid
flowchart LR
    A[External system] --> M[Mule integration]
    M -->|Publish event| E((Salesforce Event Bus))
    E --> S[Salesforce Flow / Apex subscriber]
    SF[Salesforce publisher] --> E
    E -->|Subscribe| M2[Mule consumer]
    M2 --> ERP[ERP / external API]
~~~

## 2. Publishing from Mule

The exact component configuration depends on which connector and version you choose:
- With a compatible Salesforce Connector, use its supported Platform Event publish operation.
- With the Salesforce Pub/Sub Connector, follow its publish operation and event schema requirements.
- Authenticate with the correct Salesforce permissions and API access.
- Map your internal business data to the exact Platform Event API name and field names.

A generic implementation plan:
1. Configure the Salesforce connection securely.
2. Define the event in Salesforce first, for example Inventory_Low__e.
3. Build the event payload with the exact field API names.
4. Use the connector's publish operation.
5. Handle both immediate request errors and any asynchronous publish outcome supported by that API.
6. Log a correlation/business ID and record the outcome.
7. Verify that a Salesforce subscriber actually receives and handles the event.

Avoid copying XML from a different connector release without checking its namespace, operation names, schema, and authentication options.

## 3. Real-time inventory alert example

A warehouse system detects low stock. Mule receives a webhook or polls the inventory API, then publishes an Inventory_Low__e event.

Example business fields:

~~~json
{
  "Product_Code__c": "SKU-204",
  "Warehouse_Code__c": "WH-NORTH",
  "Available_Quantity__c": 4,
  "Severity__c": "HIGH"
}
~~~

Salesforce Flow can subscribe/react to the event and notify the purchasing team or create a follow-up task. The exact action depends on your business process and Salesforce configuration.

~~~mermaid
sequenceDiagram
    participant W as Warehouse system
    participant M as Mule
    participant E as Salesforce Event Bus
    participant F as Salesforce Flow
    W->>M: Stock level changed
    M->>M: Validate and map event
    M->>E: Publish Inventory_Low__e
    E-->>F: Deliver event
    F->>F: Notify buyer / create follow-up
~~~

## 4. Platform Events vs Anypoint MQ vs JMS

These tools all support event/message-based integration, but they solve different platform needs.

| Technology | Best starting use |
|---|---|
| Salesforce Platform Events | Business events published to and consumed from Salesforce's event bus |
| Anypoint MQ | Managed messaging between applications in MuleSoft/Anypoint architecture |
| JMS with a compatible provider | Messaging through a JMS provider such as a compatible ActiveMQ deployment |
| Change Data Capture | Notifications about supported Salesforce record changes |

Choose based on where the event lives, which applications must consume it, the required delivery/retention behavior, and the connector/API compatibility. They are not interchangeable names for the same queue.

## 5. Reliability: do not assume exactly-once processing

A message may be redelivered or an integration may retry after a timeout. Design consumers to avoid duplicate business effects:
- Use an event/business identifier where available.
- Store processed IDs or apply an idempotent upsert to the downstream system.
- Distinguish “publish accepted” from “subscriber processing completed.”
- Record failed work and provide an operator-controlled replay/reconciliation path.
- Use bounded retries and the error-handling practices from Chapter 13.

A timeout after publishing can leave the caller unsure whether the event was accepted. Before republishing, use a safe deduplication strategy or verify the outcome when the API supports it.

## 6. Replay and event retention

Replay behavior depends on the Salesforce API and connector. Salesforce event messages have a retention window; replay can help a subscriber resume after a brief outage, but it is not a replacement for long-term storage.

Build a recovery plan:
1. Monitor subscriber health and delivery failures.
2. Store business processing status in a durable system when needed.
3. Know the available replay window for the event/API.
4. Reconcile business records if the outage exceeds the replay window.
5. Make replay safe through idempotency.

Do not treat Replay ID as an incremental business sequence number.

## 7. Security and monitoring checklist

- Use secure authentication and least-privilege permissions.
- Do not store credentials in source control.
- Publish only fields required by subscribers.
- Avoid secrets and unnecessary personal data in event payloads.
- Log event/business IDs and outcomes, not full sensitive payloads.
- Monitor publishing errors, subscriber health, processing latency, and downstream failures.
- Review Salesforce event usage/limits and the current org's edition and entitlements.
- Document ownership and support steps for failed events.

## 8. Capstone: Salesforce order readiness

Build a small integration with these steps:
1. Define Order_Ready__e and its fields.
2. Publish a test event from Salesforce Apex or Flow.
3. Subscribe using a compatible MuleSoft Salesforce Connector or Salesforce Pub/Sub Connector.
4. Transform the payload and send it to a mock ERP API.
5. Add error handling and safe structured logs.
6. Make processing idempotent.
7. Configure and test the supported replay/reconnect behavior.
8. Publish a second event from Mule to Salesforce, if your chosen connector/API and permissions support it.
9. Document what happens when Salesforce is unavailable, Mule is offline, or the ERP returns an error.

### Capstone acceptance criteria

- The event definition and field names are documented.
- A publisher can create an event.
- Mule receives and transforms the event.
- A downstream failure is observable and does not silently disappear.
- Duplicate events do not duplicate the business action.
- Replay and retention assumptions are documented.
- Credentials and sensitive payload data are not exposed.
