# Chapter 14.3 — Subscribe to Salesforce Platform Events from MuleSoft

Now connect the event to a Mule application. Salesforce publishes Order_Ready__e; Mule listens and processes each event.

## Architecture

~~~mermaid
sequenceDiagram
    participant SF as Salesforce
    participant EB as Salesforce Event Bus
    participant M as Mule subscriber
    participant ERP as ERP / Order API
    SF->>EB: Publish Order_Ready__e
    EB-->>M: Deliver event message
    M->>M: Log safe metadata and transform payload
    M->>ERP: Create/update order
    ERP-->>M: Result
~~~

## 1. Before you start

You need:
- Access to a Salesforce org where the Platform Event exists.
- The event and fields from lesson 14.2.
- Anypoint Studio and a Mule 4 project.
- A compatible Salesforce Connector or Salesforce Pub/Sub Connector version.
- A connected app / authentication setup permitted by your organization.

Use secure credential configuration. Do not commit usernames, passwords, client secrets, or access tokens into GitHub.

## 2. Choose the connector path

Salesforce's current MuleSoft documentation recommends considering the **Salesforce Pub/Sub Connector** for new integrations involving Platform Events and Change Data Capture. It is based on the Salesforce Pub/Sub API.

The **Salesforce Connector** also supports event subscriptions through operations such as Replay Channel Listener / Replay Channel depending on connector version. The exact supported operation names and configuration fields differ by version.

Before implementing:
1. Check your connector version and compatibility matrix.
2. Install the appropriate connector from Exchange.
3. Follow that connector's official configuration reference.
4. Use the examples below as a flow blueprint, not as a promise that all connector versions use identical component names.

## 3. Create the Mule application

1. Create a Mule project named platform-events-subscriber.
2. Add the selected Salesforce connector and configure authentication.
3. Add the event subscription source from that connector.
4. Configure the event channel for Order_Ready__e. For the Salesforce Connector's streaming-channel listener, the common path is /event/Order_Ready__e.
5. Add a Logger after the source.
6. Run the app and publish the test event from lesson 14.2.

For a Salesforce Connector streaming-channel listener, MuleSoft documentation demonstrates a source configured with a streaming channel such as /event/Cloud_News__e. For the custom event in this lesson, substitute /event/Order_Ready__e. For the Pub/Sub Connector, configure the topic/event name using the current connector reference.

## 4. Inspect the incoming event

A Salesforce streaming event payload may be wrapped in envelope metadata such as channel, schema, payload, and replay information. The exact shape depends on the selected connector and operation.

A simplified business-data example is:

~~~json
{
  "Order_Number__c": "ORD-1007",
  "Customer_Code__c": "CUST-204",
  "Order_Total__c": 149.95,
  "Status__c": "READY"
}
~~~

This is the business payload for learning purposes, not a guarantee of the complete runtime envelope. Run the listener and inspect the actual payload shape before writing DataWeave mappings.

## 5. Add logging safely

Use a Logger to record the event type, order number, and correlation identifier where available. Avoid logging the entire payload if it may contain personal, financial, or confidential information.

A conceptual log message might be:

~~~text
Received Order_Ready event for order ORD-1007
~~~

If the event wrapper nests business data under data.payload, use the path shown in the actual runtime payload. Do not guess the path; inspect the payload first.

## 6. Transform and call a downstream API

After confirming the actual payload structure:
1. Add Transform Message to map event fields into the ERP API's expected JSON.
2. Add an HTTP Request connector to call the ERP or a mock endpoint.
3. Handle non-success responses with the error-handling techniques from Chapter 13.
4. Record the business outcome using the order number and correlation ID.
5. Make downstream processing idempotent so replayed or duplicate events do not create duplicate orders.

Illustrative mapping after extracting the business fields:

~~~dataweave
%dw 2.0
output application/json
---
{
  externalOrderId: payload.Order_Number__c,
  customerCode: payload.Customer_Code__c,
  total: payload.Order_Total__c,
  status: payload.Status__c
}
~~~

Adapt payload to the real event structure shown in Studio's debugger or Logger. If your connector wraps fields in a nested envelope, map from that nested path instead.

## 7. Replay, reconnection, and duplicate safety

Streaming APIs support replay within a defined retention window, subject to the selected API, connector, and event type. Replay identifiers are opaque; do not increment them or treat them as business sequence numbers.

Plan for:
- What happens if Mule is offline.
- Which replay position/behavior is configured.
- What happens when an event is delivered again.
- How failed downstream processing is retried or routed for investigation.
- How you reconcile events older than the available replay window.

Do not assume that a replay mechanism is a permanent queue or that every failure automatically retries forever.

## 8. Test checklist

- [ ] Mule authenticates successfully.
- [ ] Subscriber connects to the correct event channel/topic.
- [ ] Publishing Order_Ready__e results in a Mule event.
- [ ] Logs show the expected order number without sensitive data.
- [ ] DataWeave maps the actual payload shape correctly.
- [ ] Downstream API success is recorded.
- [ ] Downstream failure follows a defined error policy.
- [ ] Duplicate delivery does not create duplicate business effects.
