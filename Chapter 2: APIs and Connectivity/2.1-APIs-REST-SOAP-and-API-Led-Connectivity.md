# Chapter 2: APIs, REST, SOAP, and API-Led Connectivity

## 1. What Is an API?

API stands for Application Programming Interface.

An API allows two software applications to communicate with each other and exchange data. It defines how a client can request information or perform an operation through a system.

For example, imagine an e-commerce application that needs to retrieve customer details from a database or another application. Instead of accessing the database directly, it can send a request to an API that provides the required information.

**Example**

A client sends a request:

`GET /customers/101`

The API processes the request and returns a response containing the customer's information, if the request is valid and authorized.

In simple words, an API acts as an interface through which applications communicate.

## 2. What Is a REST API?

REST stands for Representational State Transfer.

REST is an architectural style used to design web APIs. REST APIs commonly use HTTP methods to perform operations on resources.

Common HTTP methods include:

GET: Retrieve information.

POST: Create a resource or submit data for processing.

PUT: Replace an existing resource.

PATCH: Partially update an existing resource.

DELETE: Delete a resource.

**Example**

Suppose an application manages customer information.

`GET /customers/101`

Retrieves the customer with ID 101.

`POST /customers`

Sends data to create a new customer.

`PUT /customers/101`

Replaces the existing customer resource.

`PATCH /customers/101`

Updates specific fields of the customer.

`DELETE /customers/101`

Requests deletion of the customer.

These examples assume the API supports the specified operations.

REST APIs commonly exchange data using JSON, although other formats are possible.

## 3. What Is a SOAP API?

SOAP stands for Simple Object Access Protocol.

SOAP is a messaging protocol used by applications to exchange structured information. It commonly uses XML to represent messages and defines a formal structure for requests and responses.

SOAP services often use WSDL (Web Services Description Language) to describe their operations, message formats, and service endpoints.

**Example**

Suppose a banking application provides an account balance service through SOAP.

The client sends a structured XML request containing the account information. The service processes the request and returns an XML response containing the account balance or an appropriate error.

SOAP is commonly used in enterprise environments where formal service contracts, standardized messaging, and established security or transaction requirements are important.

## 4. REST API vs SOAP API

REST and SOAP are different approaches to communication between applications. REST is an architectural style, whereas SOAP is a protocol.

### REST API

- Follows REST architectural principles.
- Commonly uses HTTP methods such as GET, POST, PUT, PATCH, and DELETE.
- Commonly exchanges JSON data.
- Often uses resource-based URLs.
- Can be relatively simple to develop and consume.
- Is widely used in web applications, mobile applications, and modern integrations.

### SOAP API

- Follows the SOAP messaging protocol.
- Uses structured XML messages.
- Commonly uses WSDL to describe the service contract.
- Supports standardized SOAP fault messages.
- Can use WS-Security and other WS-* standards where required.
- Is used in enterprise integrations that require specific messaging standards or established service contracts.

> **Important:** REST APIs can also use XML, and SOAP is not limited to a particular transport in every implementation. The main distinction is that REST is an architectural style and SOAP is a protocol.

## 5. Why Do We Use APIs?

APIs allow applications to communicate without requiring each application to understand the internal implementation of the other.

Organizations use APIs to:

- Exchange data between applications.
- Expose business functionality to other systems.
- Integrate cloud applications with internal systems.
- Build web and mobile applications.
- Reuse existing services instead of duplicating functionality.
- Control access to application functionality through authentication and authorization.
- Connect systems built using different technologies.

For example, an online shopping application can use APIs to retrieve product details, create orders, process payments, and track deliveries.

## 6. When Should We Use REST or SOAP?

### When to Use REST

REST is generally a good choice when:

- Building web or mobile application APIs.
- Exchanging JSON data between systems.
- Developing lightweight services for common business operations.
- Exposing resources through standard HTTP methods.
- Creating APIs that need to be consumed by multiple applications.

**Example:** A shopping website uses a REST API to retrieve product details and create customer orders.

### When to Use SOAP

SOAP is generally a good choice when:

- Integrating with an existing SOAP-based enterprise service.
- A service requires a formal WSDL contract.
- The integration depends on WS-Security or other SOAP-related standards.
- An established enterprise system requires SOAP messages.
- Specific messaging, transaction, or reliability standards are part of the service requirements.

**Example:** A banking system integrates with an existing SOAP service that provides account information and requires a defined XML message contract.

### How to Choose

Choose REST when it meets the application's requirements and offers the simplest suitable approach.

Choose SOAP when the existing service, formal contract, or required enterprise standards call for it.

Neither approach is automatically more secure. Security depends on the implementation, configuration, and applicable requirements.

## 7. What Is API-Led Connectivity?

API-led connectivity is an architectural approach promoted by MuleSoft for organizing integrations into three layers: System APIs, Process APIs, and Experience APIs.

Each layer has a specific responsibility. This separation helps developers reuse integration logic and reduces direct dependencies between applications.

The three layers are:

1. System API
2. Process API
3. Experience API

## 8. The Three Layers of API-Led Connectivity

### A. System API

A System API provides controlled access to an underlying system, such as a database, CRM, ERP, or legacy application.

Its main responsibility is to expose the required system data or functionality without forcing consuming applications to understand the system's internal details.

**Example**

A Customer System API connects to a CRM and provides access to customer information.

### B. Process API

A Process API combines, coordinates, or transforms data and business logic from one or more systems.

Its main responsibility is to implement reusable business processes independently of a particular user interface.

**Example**

A Customer Order Process API retrieves customer information, checks inventory, and combines the required information to support an order process.

### C. Experience API

An Experience API presents data and functionality in a format suited to a particular consuming application or channel.

Its main responsibility is to make backend capabilities convenient for that application's needs.

**Example**

A Mobile Shopping Experience API provides a mobile application with the customer and order information it needs.

## 9. One Complete Example of API-Led Connectivity

Consider an e-commerce company that has the following systems:

- CRM: Stores customer information.
- Inventory system: Stores product availability.
- Order system: Stores customer orders.
- Web application: Used by customers to shop.
- Mobile application: Used by customers to shop on their phones.

Without a reusable integration architecture, the web and mobile applications might each need their own integrations with several backend systems. This can duplicate logic and increase maintenance effort.

With API-led connectivity, the company can organize its APIs as follows.

### System Layer

Customer System API connects to the CRM.

Inventory System API connects to the inventory system.

Order System API connects to the order management system.

### Process Layer

Order Process API uses the relevant System APIs to coordinate order-related business logic, such as retrieving customer information and checking product availability.

### Experience Layer

Web Experience API provides the data required by the website.

Mobile Experience API provides the data required by the mobile application.

### Overall Architecture

```text
Web Application ──> Web Experience API ──┐
                                         │
                                         v
                                  Order Process API
                                         ^
                                         │
Mobile Application ──> Mobile Experience API

Order Process API communicates with the required System APIs:

Order Process API ──> Customer System API ──> CRM

Order Process API ──> Inventory System API ──> Inventory System

Order Process API ──> Order System API ──> Order Management System
```

This is a simplified logical architecture. The exact API dependencies depend on the business requirements, and not every request needs to pass through all three layers.

### How Does This Help?

The web and mobile applications can reuse the same underlying business capabilities without independently implementing every backend integration.

If the company changes its CRM, developers may only need to update the relevant System API implementation, provided its external contract remains compatible.

If the company launches a new customer channel, it can reuse existing Process and System APIs where appropriate.

This separation improves reuse, maintainability, and flexibility.

## 10. How API-Led Connectivity Relates to MuleSoft

MuleSoft developers can implement these layers using Mule applications and APIs developed through Anypoint Platform.

A typical workflow is:

1. Identify the systems that need to communicate.
2. Design the required API contracts.
3. Build System APIs to expose system capabilities.
4. Build Process APIs to coordinate business logic.
5. Build Experience APIs for specific consuming applications.
6. Test the APIs and integrations.
7. Apply appropriate security policies and deploy the applications.

API-led connectivity is an architectural approach, not a requirement that every integration must contain exactly three APIs. The architecture should reflect the actual business needs.
