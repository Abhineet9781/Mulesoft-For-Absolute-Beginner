# Chapter 14.2 — Hands-On: Create and Publish a Salesforce Platform Event

This lesson creates a custom Salesforce Platform Event and publishes a sample event. You need access to a Salesforce org/edition that supports Platform Events and permission to create event definitions and publish messages.

## Goal

Create `Order_Placed__e` and publish an event when a sample order is ready for fulfillment.

## 1. Create the event definition

1. Log in to Salesforce.
2. Open **Setup**.
3. In Quick Find, search for **Platform Events**.
4. Open Platform Events and select **New Platform Event**.
5. Enter:
   - Label: `Order Placed`
   - Plural Label: `Orders Placed`
   - Object Name: `Order_Placed`
   - Description: `Published when an order is confirmed and ready for fulfillment.`
6. Choose the publish behavior:
   - Use **Publish After Commit** if subscribers must be able to read the Salesforce order data committed by the same transaction.
   - Use **Publish Immediately** if the event is independent of that transaction's committed data and the event should be published when the call executes.
7. Save.

Salesforce adds the `__e` suffix, so the API name is `Order_Placed__e`.

## 2. Add custom fields

In the event's Custom Fields & Relationships section, add fields such as:

| Label | API name | Suggested type |
|---|---|---|
| Order Number | `Order_Number__c` | Text |
| Customer Reference | `Customer_Reference__c` | Text |
| Total Amount | `Total_Amount__c` | Number or Currency if offered by the event field wizard |
| Source System | `Source_System__c` | Text |

Field types supported for Platform Events are limited compared with normal Salesforce objects. Follow the field-type choices available in your org. Avoid including sensitive customer or payment details unless the integration has a clear, approved need.

## 3. Publish a test event with Flow Builder

A practical low-code option is a Salesforce Flow:
1. Create a flow appropriate for your org and use case (for example, a screen flow for a controlled test or a record-triggered flow for a real order lifecycle).
2. Add the **Create Records** element configured to create a record of type `Order_Placed__e` if your Flow Builder supports that event object in the chosen flow context.
3. Map the fields, for example:
   - Order Number = `ORD-10045`
   - Customer Reference = `C-204`
   - Total Amount = `149.95`
   - Source System = `Salesforce`
4. Save and activate the flow as required.
5. Run the test path and inspect the flow debug details.

Salesforce Flow capabilities and element availability can differ by flow type and org. If your chosen flow context cannot publish the event, use the documented Apex or API publishing route instead.

## 4. Alternative: publish through Apex

For a developer test, Salesforce supports publishing Platform Events from Apex. Example pattern:

```apex
Order_Placed__e eventMessage = new Order_Placed__e(
    Order_Number__c = 'ORD-10045',
    Customer_Reference__c = 'C-204',
    Total_Amount__c = 149.95,
    Source_System__c = 'Salesforce'
);

Database.SaveResult result = EventBus.publish(eventMessage);
System.debug('Publish request accepted: ' + result.isSuccess());
```

This illustrates the publishing request. For production code, inspect errors and account for the fact that event publication is asynchronous: a successful enqueue/request result is not the same as proof that every subscriber completed its business processing.

## 5. Subscribe in Salesforce (optional verification)

You can create a Platform Event-triggered Flow that starts when `Order_Placed__e` is received. Use a simple action, such as creating an internal task or writing a permitted test result, to confirm that the event is consumed. Avoid creating an infinite loop in which the subscriber republishes the same event every time it runs.

## 6. Verify the event contract

Before moving to MuleSoft, document:
- Event API name: `Order_Placed__e`
- Streaming channel: `/event/Order_Placed__e`
- Required fields and their types.
- Publish behavior.
- Which user/app can publish and which can subscribe.
- Expected behavior when a subscriber is disconnected.
- Duplicate-processing strategy.

## 7. Common mistakes

| Symptom | What to check |
|---|---|
| Event object not found | Confirm the API name ends in `__e` and the definition is deployed/visible |
| Cannot create the event | Check org edition and required permissions |
| Subscriber cannot access fields | Check event-object permissions and connected app/API permissions |
| Subscriber sees event before record is queryable | Review Publish Immediately vs Publish After Commit |
| Publisher call succeeds but downstream work fails | Publishing and subscriber processing are separate stages; monitor the subscriber |
