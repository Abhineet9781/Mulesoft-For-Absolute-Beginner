# 16.9 — Multi-Input, Modules, Reuse, and Performance

## 1. Multiple inputs

A transformation may use the current payload, variables, attributes, and named input sources configured for a Transform Message component. In scripts, the `read` function can parse text or binary content when you know its format.

```dataweave
%dw 2.0
output application/json
var lookup = vars.productLookup default {}
---
(payload.lines default []) map ((line) -> {
  sku: line.sku,
  quantity: line.quantity,
  description: lookup[line.sku] default "Unmapped SKU"
})
```

This example uses a lookup object from a Mule variable. Ensure the variable has the expected structure before the transformation runs.

## 2. The `read` function

`read` parses a string or binary value using a specified reader MIME type. It is useful when a field contains serialized JSON or XML text rather than an already parsed object.

```dataweave
%dw 2.0
output application/json
var embedded = read(payload.embeddedJson, "application/json")
---
{
  outerId: payload.id,
  embedded: embedded
}
```

Do not parse a value that is already an object. Parsing can fail on invalid text; validate and handle that failure at the appropriate level.

## 3. Reusable modules

Create a DataWeave module file (for example, `common.dwl`) containing shared functions and types, then import the module from a script using the module syntax supported by the Mule runtime/project structure. Keep modules cohesive: date normalization belongs in a date utility, not an unrelated order transformation.

Example module concept:
```dataweave
%dw 2.0
fun normalizeEmail(value) = lower(trim((value default "") as String))
```

Use the exact import path and packaging conventions for your Mule project; Studio project structure matters.

## 4. Avoid repeated expensive work

If a calculation is used repeatedly, compute it once in a named variable. Avoid nested repeated filtering across large arrays when you can build an indexed lookup. Do not optimize prematurely: first establish correct behavior and use realistic input sizes to measure.

Less readable:
```dataweave
%dw 2.0
output application/json
---
(payload.orders default []) map ((o) -> {
  id: o.id,
  count: sizeOf((payload.lines default []) filter ((l) -> l.orderId == o.id))
})
```

This repeatedly scans lines for each order. For large data, consider grouping/indexing the lines once, then looking up each order. The best strategy depends on payload size, memory, and runtime version.

## 5. Streaming and memory

Large CSV/XML/JSON payloads may support streaming under specific reader and connector conditions. A transformation that forces all records into memory, sorts the entire collection, or repeatedly traverses it can defeat streaming benefits. Streaming depends on source format, reader settings, connector behavior, and the operations used; never assume that any DataWeave expression is streaming automatically.

## 6. Maintainability

- Name intermediate values by business meaning.
- Avoid one-line transformations that hide five unrelated operations.
- Keep target schema construction explicit.
- Use shared functions only when they express stable shared behavior.
- Document assumptions about timezone, rounding, duplicate keys, and nulls.
- Add tests for empty and malformed input.

## Practice examples

### Example 17 — Parse embedded JSON safely by contract

```dataweave
%dw 2.0
output application/json
var parsed = read(payload.details, "application/json")
---
{ id: payload.id, details: parsed }
```

This example assumes `details` contains valid JSON text. Decide what to do when it does not.

### Example 18 — Reuse a normalization function

```dataweave
%dw 2.0
output application/json
fun normalize(value) = upper(trim((value default "") as String))
---
{
  country: normalize(payload.country),
  state: normalize(payload.state),
  postalCode: normalize(payload.postalCode)
}
```
