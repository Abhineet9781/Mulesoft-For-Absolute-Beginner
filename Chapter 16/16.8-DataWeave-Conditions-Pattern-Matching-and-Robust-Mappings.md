# 16.8 — Conditions, Pattern Matching, Errors, and Robust Mappings

## 1. if / else

```dataweave
%dw 2.0
output application/json
var amount = (payload.amount default 0) as Number
---
{
  tier: if (amount >= 1000) "GOLD"
        else if (amount >= 250) "SILVER"
        else "STANDARD"
}
```

Conditions are evaluated in order. Put the most specific or highest threshold first when conditions overlap.

## 2. `match` pattern matching

Pattern matching can make multi-branch logic easier to read than deeply nested conditionals. Exact syntax and supported patterns should be checked against your runtime version.

```dataweave
%dw 2.0
output application/json
---
payload.status match {
  case "NEW" -> "Received"
  case "PAID" -> "Payment confirmed"
  case "SHIPPED" -> "On the way"
  case "CANCELLED" -> "Cancelled"
  else -> "Unknown status"
}
```

Always include a fallback when unknown values are possible. Do not map an unknown status to success.

## 3. Business rules and derived fields

```dataweave
%dw 2.0
output application/json
fun discountRate(tier) =
  if (tier == "GOLD") 0.15
  else if (tier == "SILVER") 0.08
  else 0
var amount = (payload.amount default 0) as Number
var tier = payload.tier default "STANDARD"
---
{
  tier: tier,
  discount: amount * discountRate(tier),
  payable: amount - (amount * discountRate(tier))
}
```

Keep business rules testable and avoid duplicating the same calculation in multiple fields.

## 4. Error strategy: fail, default, or report?

Three common strategies:
- **Default** only when the fallback is a legitimate business rule.
- **Validate and fail** when the input is invalid and continuing would produce misleading data.
- **Return a validation result** when the contract calls for row-level errors or a partial-success report.

DataWeave exceptions are not the same as Mule flow error handling. A failed cast or invalid selector may cause the Transform Message to fail; handle that at an appropriate Mule scope/error handler and avoid converting every error into a successful-looking empty response.

## 5. Validate required fields

```dataweave
%dw 2.0
output application/json
var missing = []
  ++ (if (payload.orderId == null) ["orderId"] else [])
  ++ (if (payload.customerId == null) ["customerId"] else [])
  ++ (if (payload.lines == null or isEmpty(payload.lines)) ["lines"] else [])
---
{
  valid: isEmpty(missing),
  errors: missing map ((field) -> {field: field, message: "Required value is missing"})
}
```

This is an illustrative validation result. In a production API, also validate types, ranges, lengths, uniqueness, and domain rules. If field presence itself matters, distinguish a missing key from a present-null key.

## 6. Partial success for batch-like input

For a list of records, decide whether one bad record should fail the whole request or be represented as an individual error. A robust row-level result may include `index`, `id`, `success`, `data`, and `errors`. Do not silently discard failed records.

## 7. Idempotent and deterministic transformations

A transformation should ideally return the same result for the same input. Avoid dependence on external mutable state. If a mapping adds current timestamps, random identifiers, or environment values, recognize that it is no longer purely deterministic and test accordingly.

## Practice examples

### Example 15 — Normalize status

```dataweave
%dw 2.0
output application/json
---
(payload.status default "unknown") match {
  case "new" -> "NEW"
  case "paid" -> "PAID"
  case "shipped" -> "SHIPPED"
  else -> upper((payload.status default "UNKNOWN") as String)
}
```

### Example 16 — Row-level validation

```dataweave
%dw 2.0
output application/json
---
(payload.records default []) map ((r, i) -> {
  index: i,
  id: r.id default null,
  valid: r.id != null and r.amount != null,
  errors: []
    ++ (if (r.id == null) ["id required"] else [])
    ++ (if (r.amount == null) ["amount required"] else [])
})
```

## Production checklist

- Validate before irreversible operations.
- Do not turn technical failures into fake business success.
- Preserve correlation IDs and record indices for diagnosis.
- Avoid logging passwords, tokens, payment card data, or unnecessary personal data.
- Test malformed, missing, null, empty, and boundary inputs.
