HTTP methods, URI parameters, request payloads, Postman testing.

## Build the worked application

1. Create crud-practice-api and separate flows for GET /tasks, POST /tasks, PUT /tasks/{taskId}, and DELETE /tasks/{taskId}. Share a global Listener config if desired.
2. GET: Set Payload to a JSON array containing two sample tasks.
3. POST: return a confirmation using the request payload, for example {message: "Task received", task: payload}.
4. PUT: use attributes.uriParams.taskId and request payload to return an update confirmation.
5. DELETE: return a confirmation containing the task ID.
6. Test each method and route in Postman. This exercise does not persist changes to a database.

## Your independent practice problem

Build a /notes API with GET /notes, POST /notes, PUT /notes/{noteId}, and DELETE /notes/{noteId}. Return sensible JSON for each method and explicitly state that changes are not persisted between requests.

**Do not copy the worked example directly.** Start a new flow or project, define expected inputs and outputs first, implement it yourself, and test both normal and edge cases in Postman. The challenge intentionally has no screenshot and no solution.

## Troubleshooting checklist

- Confirm the Listener port is available and the app is running.
- Match the HTTP method and route exactly.
- For JSON requests, use Postman Body → raw → JSON.
- Query parameters are available under attributes.queryParams; URI template values are under attributes.uriParams.
- payload is the current message body, vars contains variables, and attributes describes the current message.
- HTTP Request replaces the current payload with its response unless you preserve the original data in a variable first.
