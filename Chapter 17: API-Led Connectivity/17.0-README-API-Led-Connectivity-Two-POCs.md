# Chapter 17 — API-Led Connectivity: Two End-to-End Mule 4 POCs

This chapter builds the same small business integration in two ways so you can compare **contract-first development with RAML/APIkit** against **manual implementation without RAML**. Both POCs use all three API-led connectivity layers:

- **System API** — provides controlled access to a backend system or data source.
- **Process API** — combines data and applies business orchestration.
- **Experience API** — exposes a consumer-friendly contract for a particular channel.

> **Learning target:** You should be able to explain the responsibility of each layer, implement the request path across all three, test the layers independently, and describe when RAML/APIkit is useful. These are local learning POCs, not production-ready deployments.

## What you will build

A simple **Customer 360** API. A consumer requests a customer summary; the Experience API calls the Process API, which retrieves a customer record from the System API and combines it with an order summary. To keep the exercise self-contained, the System API uses in-memory sample data rather than a real database.

| Layer | Local base URL | Responsibility |
|---|---|---|
| System API | `http://localhost:8081/api` | Return a customer record from sample data |
| Process API | `http://localhost:8082/api` | Call System API and enrich/reshape the result |
| Experience API | `http://localhost:8083/api` | Expose `GET /customers/{customerId}/summary` for a consumer |

Ports are examples. Change them if they conflict with another local application.

## Suggested order

Complete POC 1 first, then rebuild the same behavior as POC 2. Do not combine the two approaches into one app: keeping the apps separate makes the network calls and layer responsibilities visible.

## Important implementation notes

- Each layer is a separate Mule application for clarity. Run all three locally at the same time.
- Use HTTP Listener for inbound calls and HTTP Request for calls to the next layer.
- The RAML contract describes the Experience API; APIkit scaffolds routing, but it does not automatically implement business logic or create all three API-led layers.
- The System API is intentionally a stub. Replacing sample data with a database, Salesforce, SAP, or another source is a future extension.
- Avoid logging credentials, authorization headers, or real customer personal data.
- A successful local POC does not by itself provide authentication, TLS, retries, idempotency, deployment configuration, or production observability.
