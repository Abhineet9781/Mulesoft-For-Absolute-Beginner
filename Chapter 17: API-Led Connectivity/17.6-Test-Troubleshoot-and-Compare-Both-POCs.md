# 17.6 — Test Both POCs, Troubleshoot, and Compare

This lesson makes the comparison meaningful: the architecture and expected API behavior should stay the same while the specification/scaffolding approach changes.

## 1. Test matrix

Run these tests for both POCs.

| Test | Request | Expected result |
|---|---|---|
| System API success | `GET :8081/api/customers/C-100` | 200 with customer record |
| System API second record | `GET :8081/api/customers/C-200` | 200 with second customer |
| System API unknown ID | `GET :8081/api/customers/C-999` | 404 with structured error |
| Process API success | `GET :8082/api/customer-summary/C-100` | 200 with customer and order summary |
| Experience API success | `GET :8083/api/customers/C-100/summary` | 200 with Experience API response shape |
| Experience API unknown ID | `GET :8083/api/customers/C-999/summary` | 404 with documented error |
| Wrong HTTP method | `POST :8083/api/customers/C-100/summary` | 405 or documented router behavior |
| Process API stopped | Call Experience while port 8082 is unavailable | Controlled upstream failure, not misleading success |
| System API stopped | Call Process while port 8081 is unavailable | Controlled dependency failure |

The exact HTTP status for an unsupported method depends on the Listener/router configuration; document and verify the behavior you choose. Do not assume every manually configured Listener returns 405 automatically.

## 2. Compare the results

The following should remain consistent between POC 1 and POC 2:

- Endpoint path and method.
- Success JSON structure.
- Error structure and status semantics.
- Layer responsibilities and request direction.
- DataWeave business mapping.
- Downstream dependency behavior.

The implementation structure differs:

| Area | POC 1: RAML + APIkit | POC 2: no RAML |
|---|---|---|
| Contract definition | RAML file | Written/manual documentation and implementation |
| Route scaffolding | APIkit generates routing structure | Configure Listener/routes manually |
| Contract visibility | Explicit types and response examples | Depends on documentation discipline |
| Initial setup | Requires valid spec and import/scaffolding | Often quick for a tiny one-route demo |
| Contract drift | Easier to detect with spec validation and review | Easier to drift unless separately tested |
| Business logic | Still implemented by developer | Still implemented by developer |
| All three layers | Must still be designed and implemented | Must still be designed and implemented |
| Runtime security | Not provided merely by RAML | Not provided by absence of RAML either |

RAML/APIkit is not automatically “more secure” or “more performant.” It mainly improves contract clarity, scaffolding, and consistency when used with validation, tests, and governance.

## 3. Troubleshooting guide

### Port already in use

Stop the other application using the port, or change the listener port and update every downstream HTTP Request configuration.

### Connection refused

Confirm the downstream app is running, the host/port are correct, and the HTTP Request is configured for the correct base path.

### 404 from a valid endpoint

Check for duplicate base paths, URI-template syntax, exact capitalization, HTTP method, and whether the ID is present in the sample data.

### 200 with an error object

The body and HTTP status are configured separately. Explicitly set status code 404 in the not-found path and confirm it with `curl -i`.

### Process or Experience mapping fails

Inspect the actual payload before the Transform Message. A DataWeave expression can be correct for one structure and fail if a connector returns a different shape. Align the contract and mapping rather than adding arbitrary defaults to hide the mismatch.

### Unknown ID appears as a timeout

Separate domain errors (customer not found) from infrastructure errors (downstream unavailable or timed out). Configure timeouts and error handlers deliberately.

### RAML import fails

Validate RAML syntax first, check the parser's line/column message, and confirm the Studio/APIkit version supports the import workflow you selected.

## 4. A better production-shaped design

After the basic POCs work, consider the following improvements:

- Externalize host/port values to configuration properties.
- Add authentication and authorization at the appropriate edge and between services as required.
- Set connection and response timeouts.
- Map upstream errors to stable public error responses without leaking internal stack traces.
- Add correlation IDs and structured, privacy-safe logs.
- Write MUnit tests for mappings and error paths.
- Avoid hardcoding order totals; obtain them from a proper System API or business service.
- Apply API versioning, design review, governance, and deployment monitoring.
- Consider retries only for appropriate transient failures and only when the operation is safe to repeat.
