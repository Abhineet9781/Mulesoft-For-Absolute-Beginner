# 19.1 — Database Integration Fundamentals and Architecture

## 1. What is database integration?

A Mule application often receives requests from a consumer API and must read or modify data stored in a relational database. The Database Connector executes SQL using JDBC, while DataWeave maps request payloads to SQL input parameters and maps result rows to the public API response.

MuleSoft's Database Connector supports JDBC databases, including MySQL, SQL Server, Oracle, and Derby; generic JDBC configuration supports other JDBC-compliant databases. See the [official connector overview](https://docs.mulesoft.com/db-connector/latest/).

## 3. Components you need

| Component | Responsibility |
|---|---|
| HTTP Listener | Accept REST requests from a client |
| Database Config | Store connection/provider settings for reuse |
| MySQL JDBC driver | Enable Java/Mule to communicate with MySQL |
| Database operation | Execute SQL or call a stored procedure |
| Transform Message | Convert request/result formats |
| Error handler | Translate operational errors to deliberate API responses |
| MySQL server/schema | Persist the data |

## 4. Database Connector versus Database Config

- **Database Config** is a reusable global configuration: connection provider, JDBC driver, host, port, database, credentials, pool/reconnection/transaction choices.
- **Database Connector operations** are processors or sources used in a flow, such as Select or Insert.
- **SQL** expresses the database action.
- **Input parameters** bind values safely to placeholders; they are not arbitrary SQL fragments.

In Studio, each endpoint can be its own HTTP Listener flow. This is clearer for a beginner than mixing every operation into a single complex flow. Private flows/subflows may later extract shared validation, response construction, and error handling.

## 6. Design principles

1. Never concatenate user input directly into SQL text.
2. Use placeholders and input parameters for user-supplied values.
3. Give the Mule app a least-privilege MySQL account rather than using root.
4. Keep credentials in secure/environment properties.
5. Decide what an empty result means: empty list, 404, or another contract-specific response.
6. Make transaction boundaries explicit for multi-step operations.
7. Never return raw SQL errors, credentials, JDBC URLs, or stack traces to API clients.
