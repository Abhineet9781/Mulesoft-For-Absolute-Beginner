# 19.7 — TLS Troubleshooting, Diagnostics, and Flow Snapshots

## 1. Start by locating the failure layer

~~~mermaid
flowchart TD
    A[Request fails] --> B{Did TCP connect?}
    B -- No --> C[DNS, host, port, firewall, listener]
    B -- Yes --> D{Did TLS handshake complete?}
    D -- No --> E[Certificate, trust, hostname, key, protocol, cipher]
    D -- Yes --> F{Did HTTP request reach app?}
    F -- No --> G[Proxy, routing, client behavior]
    F -- Yes --> H{HTTP status indicates failure?}
    H -- 401 / 403 --> I[Authentication or authorization]
    H -- 4xx / 5xx --> J[API contract or application error]
    H -- Success --> K[Inspect business payload]
~~~

Do not treat every connection error as a certificate error. First determine whether DNS/TCP connectivity, TLS negotiation, HTTP routing, or application logic failed.

## 2. Flow snapshot — inbound HTTPS Listener

~~~mermaid
flowchart TD
    A[HTTPS Listener: port 8443] --> B[Transform Message]
    B --> C[HTTP response]
    A -. TLS identity .-> D[Listener keystore]
    A -. optional mTLS validation .-> E[Client truststore]
~~~

## 3. Flow snapshot — outbound HTTPS Requester

~~~mermaid
flowchart TD
    A[Trigger] --> B[HTTP Requester: HTTPS URL]
    B --> C{Server chain trusted?}
    C -- Yes --> D{Hostname and certificate checks pass?}
    D -- Yes --> E[Process response]
    C -- No --> F[Trust / PKIX error]
    D -- No --> G[Hostname verification error]
    B -. optional client identity for mTLS .-> H[Client keystore]
    B -. validates remote server with .-> I[Truststore]
~~~

## 4. Common errors and likely causes

| Symptom / message fragment | Likely causes | Correct checks |
|---|---|---|
| `PKIX path building failed` | No valid path to a trusted CA; missing intermediate; wrong truststore | Inspect presented chain, trust anchors, store path/type |
| `unable to find valid certification path` | Certificate issuer not trusted | Verify issuer and import approved CA certificate |
| `No subject alternative DNS name matching` | URL hostname not in SAN | Use the correct DNS name or reissue certificate with correct SAN |
| `CertificateExpiredException` | Expired leaf/intermediate/root or local clock issue | Check all chain validity dates and system clock |
| `UnrecoverableKeyException` | Wrong key password or inaccessible key entry | Check alias, entry type, key password |
| `Keystore was tampered with, or password was incorrect` | Wrong password, wrong file, unsupported format/corruption | Verify file and store type/password |
| `handshake_failure` | Protocol/cipher mismatch, mTLS requirement, key usage, server policy | Check both endpoints' TLS policy and certificate requirements |
| `Received fatal alert: certificate_unknown` | Peer rejected presented certificate or chain | Inspect peer trust configuration and logs |
| `Connection refused` | No listener, wrong port, firewall or host | Verify process, bind address, port and TCP reachability |
| HTTP 401/403 | TLS likely completed; application authentication/authorization failed | Inspect API credentials, scopes, client identity mapping |
| HTTP 415 | Unsupported media type | Check HTTP Content-Type, not certificate trust |
| HTTP 5xx | Remote or local application/server error | Correlation ID and application logs |

Exact exception text varies by JDK, Mule version, connector, and TLS provider.

## 5. Inspect certificates

~~~bash
keytool -list -v -keystore mule-server.p12 -storetype PKCS12
keytool -printcert -file server.cer
~~~

Check the SAN, validity, issuer, chain length, and key usages. Confirm the actual certificate served by the endpoint rather than assuming the local file matches it.

If OpenSSL is available, you can inspect a server handshake:

~~~bash
openssl s_client -connect localhost:8443 -servername localhost -showcerts
~~~

This is a diagnostic command, not proof that the endpoint is secure. Review the verification result and ensure the right CA/hostname checks are applied. Tool options differ by OpenSSL version.

## 6. Java TLS debug logging

For a short, controlled local investigation, Java supports TLS debug options such as:

~~~text
-Djavax.net.debug=ssl,handshake
~~~

Enable only temporarily and avoid sharing raw debug logs publicly. Logs can be large and may reveal endpoint metadata, certificate details, or operational information. Do not leave verbose TLS debugging enabled in production without a clear need and approval.

## 7. Safe troubleshooting workflow

1. Capture the full error and timestamp.
2. Identify whether the failing connection is inbound to Mule or outbound from Mule.
3. Record the target host, port, runtime version, connector version, and TLS context name.
4. Check system time and certificate validity.
5. Inspect the actual leaf certificate and full chain.
6. Confirm hostname/SAN match.
7. Confirm the intended CA/peer is trusted.
8. Check alias, store type, path, permissions, and passwords without exposing their values.
9. If mTLS is used, inspect both sides' client-certificate requirements and trust configuration.
10. Test again with normal verification enabled.
11. Document the root cause and a safe fix, not only a workaround.

## 8. Never use these as permanent fixes

- Disabling hostname verification.
- Trusting all certificates.
- Turning off TLS validation.
- Importing an unknown certificate from an error message without verifying its fingerprint.
- Replacing a certificate chain with a random leaf certificate.
- Printing private keys or passwords into logs.
- Returning HTTP 200 when the TLS connection or downstream call failed.
