# 19.5 — Configure Outbound HTTPS with a Truststore

## Goal

Make a Mule HTTP Requester call a remote HTTPS service and understand how Mule decides whether the server certificate is trusted.

## Request flow

~~~mermaid
flowchart LR
    A[Inbound trigger / Scheduler] --> B[HTTP Requester: https://api.example.test]
    B --> C{TLS certificate validation}
    C -- Trusted chain + matching hostname --> D[Receive response]
    C -- Validation failure --> E[TLS handshake error]
    D --> F[Map response]
~~~

## 1. Default trust

For public HTTPS endpoints, the JVM's default trust configuration often contains public root CA certificates. Whether the target is trusted also depends on the runtime, configured TLS context, proxy, server chain, hostname, and current certificate status. Do not assume every remote service is trusted just because it uses HTTPS.

## 2. When do you need a custom truststore?

A custom truststore is often needed when the remote service uses:
- A private organizational CA.
- A self-signed certificate in a controlled environment.
- A private PKI not present in the default JVM trust.
- A deliberately constrained set of trusted issuers/peers.

Do not add a certificate to a custom truststore just to suppress an error without verifying its origin and intended identity.

## 3. Create a lab truststore

Use 19.3 to export the remote server's **public certificate** or obtain the approved CA certificate through a trusted channel. Verify its fingerprint out-of-band, then import it:

~~~bash
keytool -importcert \
  -alias remote-api-lab-ca \
  -file remote-api-ca.cer \
  -keystore remote-api-truststore.p12 \
  -storetype PKCS12
~~~

Prefer trusting the appropriate CA chain rather than pinning a rotating leaf certificate when the organizational PKI design supports CA trust. In a lab using a self-signed server certificate, importing that leaf can be appropriate for demonstrating explicit trust.

## 4. Configure the HTTP Requester

In Studio:
1. Add an HTTP Requester global configuration.
2. Set the remote host and HTTPS port.
3. Configure a TLS context if custom trust is required.
4. Set the truststore path, type, and protected password.
5. Keep hostname verification enabled.
6. Configure connect/read timeouts and an error strategy.
7. Test a successful trusted endpoint and a deliberately untrusted endpoint.

Conceptual TLS fragment (adapt to the current Mule/HTTP Connector schema):

~~~xml
<tls:context name="Remote_API_TLS_Context">
    <tls:trust-store
        path="${secure::tls.truststore.path}"
        type="pkcs12"
        password="${secure::tls.truststore.password}"/>
</tls:context>
~~~

The HTTP Requester connection then references the TLS context according to the connector version. Generate the exact XML through Studio rather than treating this fragment as a complete application.

## 5. What the truststore does and does not do

It helps establish whether the presented certificate chain anchors in configured trust. It does not:
- Change the remote server certificate.
- Make a hostname mismatch safe.
- Prove the remote API's business behavior is trustworthy.
- Authenticate Mule to the server; that requires client identity material if the server requires mTLS.
- Replace token/API-key/OAuth authentication or authorization.

## 6. Error handling

Handle TLS errors as connection/security failures, not as empty business responses. Avoid catching every error and returning HTTP 200. Log useful operational metadata such as destination host, correlation ID, error category, and timestamp without exposing credentials, private keys, or sensitive payloads.

## 7. Testing strategy

- Known trusted certificate and matching hostname: connection should succeed.
- Untrusted issuer: connection should fail.
- Wrong hostname/SAN: connection should fail.
- Expired certificate: connection should fail.
- Missing intermediate: behavior depends on the presented chain and trust path; fix the server chain rather than importing random certificates.
- Wrong truststore password/path: startup or connection configuration should fail visibly.

## Practice questions
