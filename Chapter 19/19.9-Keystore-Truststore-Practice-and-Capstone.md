# 19.9 — Keystore and Truststore Practice, Labs, and Capstone

## How to practice safely

Use disposable lab certificates and a local Mule app. Keep all private-key material outside the repository. These labs document the intended build; verify exact configuration fields against your Studio, Mule runtime, and connector versions. Capture real screenshots after you execute each lab.

## Part A — Concept questions

1. What is the difference between encryption and digital signatures?
2. What does a certificate bind together?
3. Why must a client validate both certificate trust and hostname?
4. Explain private key, public key, certificate, CA, root, intermediate, and leaf.
5. What is the difference between a keystore and truststore?
6. Compare JKS, PKCS12, PEM, and DER.
7. What is a private key entry versus a trusted certificate entry?
8. What are alias, store password, and key password?
9. Why does HTTPS not prove application authorization?
10. What additional property does mTLS provide?
11. Why is importing a certificate a trust decision?
12. What causes a PKIX path building error?
13. What is a SAN and why is it required for hostname checks?
14. Why should TLS verification not be disabled to fix an error?
15. What operational events should trigger certificate rotation?

## Part B — Lab 1: Generate and inspect a lab identity

- Use keytool to create a PKCS12 server identity with SAN for localhost.
- Inspect alias, entry type, validity, and SAN.
- Export the public certificate.
- Import it into a separate client truststore.
- Confirm that the private key did not appear in the exported certificate.
- Record the commands and sanitized output, never the password.

**Acceptance criteria:** You can explain which file contains the private key and which contains only the public certificate.

## Part C — Lab 2: Inbound HTTPS

- Configure a Mule HTTPS Listener on port 8443.
- Configure the TLS context with the server identity.
- Return a small JSON payload.
- Call it with curl using the correct trusted certificate.
- Test a wrong hostname and an untrusted certificate; both should fail verification.

**Acceptance criteria:** You demonstrate a successful verified request without using `-k` / `--insecure`.

## Part D — Lab 3: Outbound HTTPS with a custom truststore

- Configure an HTTP Requester to call a test HTTPS endpoint.
- Use the default JVM trust where appropriate, then compare with a custom truststore for a private/test CA.
- Test an untrusted server and a hostname mismatch.
- Map TLS connection failures to safe, observable error behavior.

**Acceptance criteria:** You can identify which truststore validates the remote server and explain why the endpoint's hostname matters.

## Part E — Lab 4: mTLS

- Configure an approved test client identity with a private key and certificate chain.
- Configure Mule's HTTP Requester with the client keystore and server truststore.
- Configure the test server to request and trust the client certificate.
- Test with a valid client certificate, no client certificate, and a certificate from an untrusted issuer.
- Test application authorization independently of TLS authentication.

**Acceptance criteria:** A valid certificate completes the TLS handshake, while missing/untrusted identities fail according to the server policy. A trusted client without application permission is still denied the protected operation.

## Part F — Troubleshooting drill

For each failure, identify the likely layer and the safest next check:
- Wrong keystore password.
- Wrong private-key alias.
- Expired server certificate.
- Missing intermediate CA.
- SAN mismatch.
- Untrusted server issuer.
- Remote server rejects client certificate.
- TLS succeeds but API returns 403.
- TCP connection refused.
- Certificate is renewed but a pinned-leaf truststore still has the old certificate.

Write a short incident report with symptom, evidence, root cause, correction, and prevention.

## Capstone — Secure Partner API Integration

### Scenario

A Mule application exposes an HTTPS endpoint to a partner and also calls a partner's protected HTTPS API. The partner requires client-certificate authentication for outbound calls. Both connections must have separate, documented trust policies.

### Architecture

~~~mermaid
flowchart LR
    P[Partner client] -->|Inbound HTTPS / optional mTLS| M[Mule API]
    M --> F[Business flow]
    F -->|Outbound HTTPS + client certificate| R[Partner API]
    M -. presents server identity .-> KS[Inbound keystore]
    M -. validates partner client cert .-> IT[Inbound truststore]
    F -. validates partner server .-> OT[Outbound truststore]
    F -. presents Mule client identity .-> CK[Outbound client keystore]
~~~

### Deliverables

1. Diagram showing both TLS connections and every store's purpose.
2. Table listing each keystore/truststore, entry purpose, owner, environment, and rotation plan. Do not include passwords or private key content.
3. Inbound HTTPS Listener with a working test.
4. Outbound HTTP Requester with a working test.
5. mTLS test cases for valid, missing, and untrusted client certificates.
6. Hostname mismatch and expiry test cases.
7. Error handling and sanitized diagnostic logs.
8. Certificate inventory and rotation runbook.
9. Real Studio canvas screenshots and test-client results.
10. A security review explaining authorization, secret storage, network restrictions, and production gaps.

## Interview questions

1. Mule calls an HTTPS API and gets PKIX path building failed. Explain your diagnostic process.
2. The certificate is trusted but the hostname does not match. Why should Mule fail?
3. A keystore contains the certificate but no private key entry. Can Mule present that identity?
4. What is the difference between server trust and client authentication in mTLS?
5. Why can a successful TLS handshake still result in HTTP 403?
6. How would you rotate a partner CA without a planned outage?
7. What should be done if a client private key is accidentally committed to GitHub?
8. What evidence proves that a PDF/HTTP API is using the expected certificate and chain?
9. What is the risk of trusting an entire CA for client authentication when that CA issues many unrelated certificates?
10. What is your production checklist before enabling mTLS for a partner?
