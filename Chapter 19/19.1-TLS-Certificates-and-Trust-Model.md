# 19.1 — TLS, Certificates, and the Trust Model

## 1. What problem does TLS solve?

Transport Layer Security (TLS) protects data while it travels between two endpoints. It provides:
- **Confidentiality:** passive observers should not be able to read protected traffic.
- **Integrity:** changes to protected traffic are detected.
- **Peer authentication:** the endpoint can prove possession of a private key associated with a certificate. In normal HTTPS, the server authenticates itself to the client.
- **Optional client authentication:** with mutual TLS, the server also requests and validates a client certificate.

TLS does not automatically decide whether an authenticated user is allowed to access a business operation. Authorization belongs to the application/security design.

## 2. Public key and private key

A key pair has mathematically related keys:
- The **private key** must remain secret and is used for operations such as signing or proving possession during a handshake.
- The **public key** can be distributed and is included in a certificate.
- A certificate binds a public key to an identity and is signed by an issuer.

Never send the private key to a remote API merely to let it trust you. Share the public certificate when client-certificate trust is required.

## 3. What is an X.509 certificate?

Common fields include:
- Subject: identity represented by the certificate.
- Subject Alternative Name (SAN): DNS names/IP addresses the certificate is valid for.
- Issuer: CA or entity that signed the certificate.
- Validity window: Not Before and Not After.
- Public key and algorithm.
- Key Usage and Extended Key Usage.
- Serial number.
- Signature and signature algorithm.

For modern TLS hostname validation, SAN is the important hostname source. Do not rely on a Common Name alone. A certificate for `api.example.com` does not automatically match `localhost` or another DNS name.

## 4. Certificate chain and CA trust

A typical chain is:

~~~mermaid
flowchart TD
    R[Trusted Root CA] --> I[Intermediate CA]
    I --> S[Server certificate: api.example.test]
    S --> K[Server proves possession of matching private key]
~~~

A client validates the certificate chain back to a trust anchor it accepts, checks validity and usages, and verifies the requested hostname. The server normally presents its leaf certificate and required intermediate certificates. Root certificates are commonly distributed as trust anchors separately.

A self-signed certificate signs itself. It is not automatically trusted simply because it is self-signed. The client must explicitly trust it or trust an issuing CA.

## 5. TLS handshake in plain language

~~~mermaid
sequenceDiagram
    participant C as Client
    participant S as Server
    C->>S: ClientHello (supported TLS options)
    S->>C: ServerHello + certificate chain
    C->>C: Validate chain, validity, and hostname
    C->>S: Key agreement / handshake proof
    S->>C: Finished
    C->>S: Finished
    C->>S: Encrypted application data
~~~

The exact messages differ by TLS version and negotiated authentication/key-exchange method. TLS 1.3 has a different, streamlined handshake from older versions. The diagram is conceptual.

## 6. TLS vs HTTPS vs mTLS

| Term | Meaning |
|---|---|
| TLS | Cryptographic protocol protecting a connection |
| HTTPS | HTTP carried over TLS |
| Server-authenticated TLS | Client validates server identity; typical public HTTPS |
| Mutual TLS (mTLS) | Both sides authenticate with certificates during TLS setup |
| Certificate pinning | Client restricts accepted identity/key/certificate beyond ordinary CA trust; adds rotation and operational complexity |

## 7. Why a keystore and a truststore are different

Imagine a hotel:
- The **keystore** is like the hotel's own identity document and proof that it controls that identity.
- The **truststore** is like the hotel's list of authorities/identities it accepts as valid.

For an inbound HTTPS Listener, Mule needs its own server private key and certificate chain to present. For an outbound HTTPS Requester, Mule needs to trust the remote server's certificate chain. These are different questions and usually different configuration properties.

## 8. Common incorrect assumptions

- “HTTPS means every certificate is trusted.” False.
- “A truststore contains the private key for the remote server.” Usually false; it normally contains public certificates used as trust anchors.
- “If the chain is trusted, the hostname must match.” False; hostname verification is separate.
- “A certificate is secret.” Public certificates generally are not secret; private keys and passwords are.
- “mTLS replaces authorization.” False.
- “Importing any certificate fixes TLS.” It may make an unintended identity trusted and weaken security.
