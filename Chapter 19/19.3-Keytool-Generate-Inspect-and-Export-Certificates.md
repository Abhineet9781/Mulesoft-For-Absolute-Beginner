# 19.3 — Generate, Inspect, and Export Certificates with keytool

## Before starting

Run these commands in a terminal that uses a JDK with `keytool`. Check the Java version used by Anypoint Studio and the Mule runtime; a terminal can use a different JDK.

Create a lab directory **outside the Git repository** and use a lab-only password. The commands below are examples for a disposable local lab. They are not a production PKI design.

~~~bash
java -version
keytool -help
mkdir tls-lab
cd tls-lab
~~~

Use your shell's secure secret-entry mechanism in real environments. Avoid putting production passwords directly in command history, CI logs, screenshots, or process listings.

## 1. Create a self-signed server certificate for a local lab

A self-signed certificate is useful for a closed lab, but clients will not trust it automatically. Include the exact hostname you will use in the SAN. This example uses localhost:

~~~bash
keytool -genkeypair \
  -alias mule-server \
  -keyalg RSA -keysize 3072 \
  -sigalg SHA256withRSA \
  -validity 90 \
  -dname "CN=localhost, OU=Lab, O=Example, L=Delhi, ST=Delhi, C=IN" \
  -ext "SAN=dns:localhost,ip:127.0.0.1" \
  -keystore mule-server.p12 \
  -storetype PKCS12
~~~

The tool prompts for a store password. Depending on the JDK/provider, the key password may be prompted for or must be compatible with the store password. Keep it consistent with the Mule configuration you later use.

**What this creates:** a PKCS12 keystore containing a private key and self-signed certificate under alias `mule-server`. It does not create a publicly trusted certificate.

## 2. Inspect the store

~~~bash
keytool -list -v -keystore mule-server.p12 -storetype PKCS12
~~~

Check:
- Alias.
- Entry type (for identity, expect a private key entry).
- Certificate validity dates.
- Subject and issuer.
- SAN extension.
- Key usage / extended key usage, if present.
- Certificate chain length.

Never paste the private key into chat, tickets, logs, or documentation.

## 3. Export only the public certificate

~~~bash
keytool -exportcert -rfc \
  -alias mule-server \
  -keystore mule-server.p12 \
  -storetype PKCS12 \
  -file mule-server.cer
~~~

The exported certificate is public material; it does not contain the matching private key. Inspect it:

~~~bash
keytool -printcert -file mule-server.cer
~~~

## 4. Create a truststore and import the lab certificate

~~~bash
keytool -importcert \
  -alias mule-server-lab \
  -file mule-server.cer \
  -keystore mule-client-truststore.p12 \
  -storetype PKCS12
~~~

Read the certificate fingerprint and verify it through a trusted channel before accepting the import. A confirmation prompt is a security decision. This truststore trusts this exact self-signed certificate; certificate renewal may require updating it.

## 5. Verify the truststore

~~~bash
keytool -list -v \
  -keystore mule-client-truststore.p12 \
  -storetype PKCS12
~~~

For this entry, expect a trusted certificate entry rather than a private key entry.

## 6. Create a certificate signing request (CSR)

In a real CA-based workflow, a private key is generated and kept under your control, then a CSR is submitted to the approved CA. The CA returns a signed certificate and chain.

~~~bash
keytool -certreq \
  -alias mule-server \
  -keystore mule-server.p12 \
  -storetype PKCS12 \
  -file mule-server.csr \
  -ext "SAN=dns:api.example.test"
~~~

The CA must issue a certificate whose SANs, usages, validity, and policy match the intended endpoint. Ensure SAN requirements survive the CA issuance workflow; do not assume every CA copies requested extensions automatically.

## 7. Import a CA chain and signed certificate

For a CA-issued identity, import the relevant CA certificates in the order and manner required by the chosen workflow, then import the issued certificate under the alias that owns the private key. Exact import steps depend on the CA chain and tooling; back up the lab keystore before changing it.

Typical conceptual sequence:
1. Verify the root CA certificate fingerprint out-of-band.
2. Import the trusted root CA certificate if required by the keystore workflow.
3. Import intermediate certificates as needed.
4. Import the signed leaf certificate back into the same private-key alias.
5. Re-run `keytool -list -v` and confirm the private key entry has the expected chain.

Do not import an unrelated leaf certificate into a server identity store and assume it replaces the existing identity.

## 8. Convert formats carefully

Some environments need PEM, while Java connectors commonly use JKS or PKCS12. Conversion should preserve the intended private key and certificate chain and should be performed only with trusted tools and protected output files. Do not upload a private-key-containing PFX/P12 to an online converter.

Before converting, identify:
- Input file format and whether it contains a private key.
- Required output format and store type.
- Alias expectations.
- Store/key password behavior.
- Whether the chain is complete.
- How the output will be securely transferred and deleted.

## 9. Useful inspection commands

~~~bash
# List entries and details
keytool -list -v -keystore mule-server.p12 -storetype PKCS12

# Print certificate details from an exported certificate
keytool -printcert -file mule-server.cer

# Export public certificate only
keytool -exportcert -rfc -alias mule-server \
  -keystore mule-server.p12 -storetype PKCS12 \
  -file mule-server.cer
~~~

## 10. Lab cleanup

Delete disposable private-key files securely according to your environment's data-handling policy. Do not delete or rotate shared production material as part of this exercise. Keep the entire lab directory out of Git:

~~~gitignore
# Lab key material — do not commit
*.jks
*.p12
*.pfx
*.p7b
*.p7c
*.key
*-private.pem
tls-lab/
~~~

A .cer or .crt file is often public certificate material, but inspect what it contains before sharing. Avoid blanket assumptions based on extensions.
