# 19.6 — POC Part 1: Employee API — Create and Read

This is the first part of a single CRUD POC. Finish the database setup in 19.2 and MySQL Database Config in 19.3 before creating the flows.

## POC folder/model assumptions

- Mule app name: `employee-database-api`
- HTTP Listener port: `8081`
- Database Config global name: `MySQL_Database_Config`
- Schema/table: `mule_learning.employees`
- Credentials: environment/secure properties; do not hardcode secrets in source.

## Step 1 — Create the Insert flow

In Studio, create an HTTP Listener flow with:
- Path: `/api/employees`
- Method: POST
- Port from shared HTTP Listener Config on 8081

Drag **Database > Insert** into the flow. Select `MySQL_Database_Config`. Use SQL:

~~~sql
INSERT INTO employees
(first_name, last_name, email, department, salary)
VALUES (:firstName, :lastName, :email, :department, :salary)
~~~

Set Input Parameters to:

~~~dataweave
#[{
  firstName: payload.firstName,
  lastName: payload.lastName,
  email: payload.email,
  department: payload.department,
  salary: payload.salary
}]
~~~

This is the intended parameter mapping. Validate that all fields exist, have expected types, and salary is non-negative before the Insert operation. Ensure the required `db:insert` properties and namespaces are generated by Studio for your installed connector version.

## Request example

~~~http
POST http://localhost:8081/api/employees
Content-Type: application/json

{
  "firstName": "Asha",
  "lastName": "Sharma",
  "email": "asha.sharma@example.test",
  "department": "Engineering",
  "salary": 85000.00
}
~~~

## Response contract

On success, return HTTP 201 with a response shaped like:

~~~json
{
  "message": "Employee created",
  "email": "asha.sharma@example.test"
}
~~~

If your connector operation exposes a generated key using the configuration supported by your version, return the actual generated ID as part of the response. Do not invent an ID or assume output field names; inspect the Insert result in Studio/runtime.

## Flow snapshot: List employees

~~~mermaid
flowchart TD
    A[HTTP Listener GET /api/employees] --> B[Database Connector Select]
    B --> C[Transform result rows to API JSON]
    C --> D[HTTP 200 response]
~~~

SQL:

~~~sql
SELECT id, first_name, last_name, email, department, salary, created_at
FROM employees
ORDER BY id;
~~~

Transform Message after Select:

~~~dataweave
%dw 2.0
output application/json
---
payload map (row) -> {
  id: row.id,
  firstName: row.first_name,
  lastName: row.last_name,
  email: row.email,
  department: row.department,
  salary: row.salary,
  createdAt: row.created_at
}
~~~

Set Listener path to `/api/employees`, method to GET. The Select returns rows; mapping each row creates the public API JSON array.

## Flow snapshot: Get one employee

~~~mermaid
flowchart TD
    A[HTTP Listener GET /api/employees/{id}] --> B[Validate path id]
    B --> C[Database Connector Query Single]
    C --> D[Map one record]
    D --> E[HTTP 200 JSON]
    C -. no row .-> F[404 Not Found]
~~~

SQL:

~~~sql
SELECT id, first_name, last_name, email, department, salary, created_at
FROM employees
WHERE id = :id;
~~~

Input parameters:

~~~dataweave
#[{ id: attributes.uriParams.id as Number }]
~~~

Validate that the path ID is a positive integer before using it. Configure Query Single to match the expected one-row result. Depending on version and configuration, inspect whether the output for no matching record is null/empty or raises a connector error; implement the not-found response to match the observed behavior.
