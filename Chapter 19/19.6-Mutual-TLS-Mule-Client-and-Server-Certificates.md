# 19.6 — Mutual TLS (mTLS): Client and Server Certificates

## 1. What mTLS adds

In ordinary HTTPS, the client validates the server certificate. In mTLS, the server also requests a client certificate and validates it. Both endpoints prove possession of the private key corresponding to their certificate.

mTLS is commonly used for service-to-service connections, partner integrations, private APIs, and environments where client-certificate identity is required.

## 2. Two-way trust

~~~mermaid
flowchart TD
    M[Mule client / HTTP Requester] -->|1. Validate server certificate| S[Remote HTTPS server]
    S -->|2. Request client certificate| M
    M -->|3. Present client certificate + prove private-key possession| S
    S -->|4. Validate client chain and policy| M
    M -->|5. Encrypted application traffic| S
    MT[Mule client keystore] -. presents client identity .-> M
    RT[Mule client truststore] -. trusts server CA .-> M
    ST[Remote server truststore / client-CA config] -. trusts client CA .-> S
~~~

There are two separate trust decisions:
- Mule trusts the remote server's certificate.
- The remote server trusts the certificate presented by Mule.

If Mule itself is the server, the equivalent configuration is reversed: Mule's Listener presents its identity from a keystore and validates incoming client certificates using a configured truststore.

## 3. Required material

For Mule calling a remote mTLS server:
- Mule client keystore: Mule private key + client certificate chain.
- Mule truststore: CA certificate(s) trusted for the remote server.
- Remote server: its own private key and server certificate.
- Remote server trust configuration: CA certificate(s) trusted for client identities.

For a remote client calling an mTLS-enabled Mule Listener:
- Mule listener keystore: Mule server private key + certificate chain.
- Mule listener truststore: CA certificate(s) accepted for client certificates.
- Client keystore: client's private key + certificate chain.
- Client truststore: CA certificate(s) trusted for Mule's server certificate.

## 4. Configuration sequence for outbound mTLS

1. Obtain a client certificate from the organization's approved CA, or create a disposable lab identity.
2. Store the client private key and certificate chain in a supported keystore.
3. Configure the Mule HTTP Requester TLS context with that keystore.
4. Configure the truststore for the remote server's issuer.
5. Keep hostname verification enabled.
6. Ensure the remote server is configured to request and trust the client certificate.
7. Test the TLS handshake and then test application authorization separately.

Conceptual XML (adapt to the exact Mule runtime and HTTP Connector schema):

~~~xml
<tls:context name="Mule_Client_mTLS_Context">
    <tls:key-store
        path="${secure::tls.client.keystore.path}"
        type="pkcs12"
        alias="mule-client"
        password="${secure::tls.client.keystore.password}"
        keyPassword="${secure::tls.client.key.password}"/>
    <tls:trust-store
        path="${secure::tls.truststore.path}"
        type="pkcs12"
        password="${secure::tls.truststore.password}"/>
</tls:context>
~~~

This fragment shows the roles of both stores; the precise XML attributes and referencing structure must be confirmed against the connector version used by the project.

## 5. Inbound mTLS on a Mule Listener

To require clients to present a certificate:
- Configure the Listener TLS context with Mule's server keystore.
- Configure a truststore for client-certificate issuers.
- Enable client authentication / need-client-auth in the TLS context as supported by your Mule version.
- Verify the actual client certificate identity and map it to an authorized client or application.
- Reject untrusted or absent certificates at the TLS layer where required.

The distinction between **want client auth** and **need client auth** matters in Java TLS configurations: “want” may request a certificate but permit clients without one, while “need” requires one. Check the exact option exposed by the runtime.

## 6. Certificate identity is not business authorization

A valid client certificate means the peer proved control of a key associated with an accepted certificate. Your application still needs a policy for:
- Which SAN/subject or certificate attributes identify the client.
- Which API scopes/operations the client may call.
- How revoked or compromised client identities are disabled.
- How certificate renewal preserves or changes identity.
- How audit logs record the authenticated client without exposing secrets.

Do not authorize a client merely because any certificate issued by a broad corporate CA is trusted.

## 7. Common mTLS failures

- Client keystore has no private key entry.
- Wrong alias selected.
- Client certificate chain incomplete.
- Remote server does not trust the client CA.
- Mule truststore does not trust the server CA.
- Server requests no client certificate, or requires a different certificate.
- Client certificate is expired or has inappropriate key usage.
- Server certificate hostname does not match the requested URL.
- TLS protocol/cipher policy is incompatible.
- The TLS handshake succeeds but the application returns 401/403 due to authorization policy.
