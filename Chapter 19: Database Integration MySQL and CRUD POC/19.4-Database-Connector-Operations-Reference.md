# 19.4 — Database Connector Operations Reference

The exact operation list depends on Database Connector version and database provider. The current official [Database Connector reference](https://docs.mulesoft.com/db-connector/latest/database-documentation) and [examples](https://docs.mulesoft.com/db-connector/latest/database-connector-examples) list these major operation families.

## 1. Core query and write operations

| Operation | Purpose | Typical result/use |
|---|---|---|
| **Select** | Execute a query returning rows | List/search results, joins, reporting |
| **Query Single** | Execute a query intended to return one record | Find one record by ID/business key |
| **Insert** | Insert one record or execute a parameterized insert | Create a row; may expose generated keys depending on SQL/driver/config |
| **Update** | Modify rows matching a condition | Update count/result |
| **Delete** | Delete rows matching a condition | Delete count/result |
| **Bulk Insert** | Execute a parameterized insert against multiple parameter maps | Batch-style many-row insert |
| **Bulk Update** | Apply an update for multiple parameter maps | Batch-style updates |
| **Bulk Delete** | Apply a delete for multiple parameter maps | Batch-style deletes |

Do not assume every insert returns a generated ID in the same shape. Inspect the operation result and configure generated-key behavior according to the connector version, SQL, and driver.

## 2. Advanced SQL operations

| Operation | Purpose | Use carefully |
|---|---|---|
| **Stored Procedure** | Call a stored procedure, including supported input/output parameters | Vendor-specific procedure syntax and parameter metadata |
| **Execute DDL** | Run Data Definition Language statements, such as CREATE/ALTER/DROP | Prefer versioned migration tooling for managed schema changes |
| **Execute Script** | Execute a script through the connector's script operation | Understand the connector's script parsing/execution semantics for your version |
| **Database source/listener operations** | Start a flow based on database records or poll/read from a source, depending on connector operation/version | Handle scheduling, duplicate processing, ordering, and watermarking deliberately |
| **Transactions** | Run operations inside a transaction boundary | Use where all-or-nothing consistency is required |
| **Data types and custom column types** | Map database-specific data types | Validate driver and database-specific behavior |

The connector's source operation names and supported options can vary by version. Check the Studio palette/reference for the exact installed version before designing a flow.

## 4. SQL templates

Use SQL appropriate for your database dialect. These queries target the chapter's MySQL `employees` table.

Select rows:

~~~sql
SELECT id, first_name, last_name, email, department, salary
FROM employees
ORDER BY id;
~~~

Select with a parameter:

~~~sql
SELECT id, first_name, last_name, email, department, salary
FROM employees
WHERE department = :department
ORDER BY last_name, first_name;
~~~

Fetch one by ID:

~~~sql
SELECT id, first_name, last_name, email, department, salary
FROM employees
WHERE id = :id;
~~~

Insert:

~~~sql
INSERT INTO employees
(first_name, last_name, email, department, salary)
VALUES (:firstName, :lastName, :email, :department, :salary);
~~~

Update:

~~~sql
UPDATE employees
SET department = :department,
    salary = :salary
WHERE id = :id;
~~~

Delete:

~~~sql
DELETE FROM employees WHERE id = :id;
~~~

## 5. Why parameterized SQL matters

Use static SQL with placeholders and bind user input through Input Parameters. This helps separate query structure from values and helps prevent SQL injection.

Safe pattern:

~~~xml
<db:select config-ref="MySQL_Database_Config">
    <db:sql><![CDATA[
        SELECT id, first_name, last_name, email, department, salary
        FROM employees WHERE department = :department
    ]]></db:sql>
    <db:input-parameters><![CDATA[#[{ department: attributes.queryParams.department }]]]></db:input-parameters>
</db:select>
~~~

This XML shape must be checked against the connector version in Studio, including namespace/configuration details.

Unsafe pattern:

~~~text
"SELECT * FROM employees WHERE email = '" ++ userSuppliedEmail ++ "'"
~~~

Do not concatenate untrusted values into SQL. Identifiers such as a table name or sort-column name usually cannot be bound as values; if these must be dynamic, validate them against a fixed allowlist and construct only from trusted constants.

## 6. Bulk operations: performance and behavior

Bulk Insert/Update/Delete accept a list of parameter maps. They reduce repeated query parsing and network overhead compared with invoking a separate single operation for every row. However, error/partial-success behavior depends on the driver and database. If all rows must commit or roll back together, use a transaction and test rollback behavior. See [official bulk-operation guidance](https://docs.mulesoft.com/db-connector/latest/database-execute-bulk).
