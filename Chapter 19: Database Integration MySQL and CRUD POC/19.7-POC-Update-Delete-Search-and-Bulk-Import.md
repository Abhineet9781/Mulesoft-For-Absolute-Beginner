# 19.7 — POC Part 2: Update, Delete, Search, and Bulk Import

Complete the same Employee Management API built in 19.6.

## 1. Update employee — PUT /api/employees/{id}

Flow snapshot:

~~~mermaid
flowchart TD
    A[HTTP Listener PUT /api/employees/{id}] --> B[Validate ID and body]
    B --> C[Database Update]
    C --> D{Affected rows?}
    D -->|Yes| E[200 or 204]
    D -->|No| F[404 Not Found]
    B -. validation error .-> G[400 Bad Request]
~~~

SQL:

~~~sql
UPDATE employees
SET first_name = :firstName,
    last_name = :lastName,
    email = :email,
    department = :department,
    salary = :salary
WHERE id = :id;
~~~

Input parameter mapping:

~~~dataweave
#[{
  id: attributes.uriParams.id as Number,
  firstName: payload.firstName,
  lastName: payload.lastName,
  email: payload.email,
  department: payload.department,
  salary: payload.salary
}]
~~~

Use Database > Update. The Update result contains the operation result/affected-row information exposed by the installed connector and JDBC driver. Inspect it in Studio, then map zero/matched rows into your chosen API contract. Validate duplicates and salary constraints.

Test:

~~~bash
curl -i -X PUT "http://localhost:8081/api/employees/1"   -H "Content-Type: application/json"   --data '{"firstName":"Asha","lastName":"Sharma","email":"asha.sharma@example.test","department":"Platform","salary":90000}'
~~~

## 2. Delete employee — DELETE /api/employees/{id}

Flow snapshot:

~~~mermaid
flowchart TD
    A[HTTP Listener DELETE /api/employees/{id}] --> B[Validate positive ID]
    B --> C[Database Delete]
    C --> D{Affected rows?}
    D -->|1 or more| E[204 No Content]
    D -->|0| F[404 Not Found]
~~~

SQL:

~~~sql
DELETE FROM employees WHERE id = :id;
~~~

Input Parameters:

~~~dataweave
#[{ id: attributes.uriParams.id as Number }]
~~~

Only delete the row selected by the validated ID. Never expose an unfiltered delete operation through a public endpoint. Decide whether deleting an unknown ID is 404 or idempotent 204 based on the API contract.

Test with a test employee, not real business data:

~~~bash
curl -i -X DELETE "http://localhost:8081/api/employees/1"
~~~

## 3. Search by department

Route: `GET /api/employees/search?department=Engineering`

SQL:

~~~sql
SELECT id, first_name, last_name, email, department, salary
FROM employees
WHERE department = :department
ORDER BY last_name, first_name;
~~~

Input parameters:

~~~dataweave
#[{ department: attributes.queryParams.department }]
~~~

Validate the query parameter, use Select, and map rows to public JSON. A missing department should be handled as a validation error or as an intentionally designed list operation with optional filtering; do not silently change the intended query.

## 4. Bulk insert

Bulk operations accept multiple parameter maps and are intended for many records that share one SQL statement structure.

Example input:

~~~json
[
  {"firstName":"Kabir","lastName":"Singh","email":"kabir.singh@example.test","department":"Engineering","salary":68000},
  {"firstName":"Mira","lastName":"Joshi","email":"mira.joshi@example.test","department":"Operations","salary":71000}
]
~~~

SQL template:

~~~sql
INSERT INTO employees
(first_name, last_name, email, department, salary)
VALUES (:firstName, :lastName, :email, :department, :salary)
~~~

In Studio, drag **Bulk Insert**, choose the same Database Config, use the SQL above, and supply a list of parameter maps. A DataWeave mapping that yields the parameter objects should be aligned with the Bulk Insert operation's expected input shape. Verify the exact UI/input mapping in the connector version installed.

Flow snapshot:

~~~mermaid
flowchart TD
    A[HTTP Listener POST /api/employees/bulk] --> B[Validate array and each record]
    B --> C[Map to list of parameter objects]
    C --> D[Database Bulk Insert]
    D --> E[Return count/result]
    B -. invalid .-> F[400 response]
    D -. DB failure .-> G[Rollback if transactional]
~~~

**Important:** bulk operations may have driver-dependent partial-success behavior. When the batch must be all-or-nothing, wrap the operation in a suitable database transaction and test rollback. See [MuleSoft bulk operation guidance](https://docs.mulesoft.com/db-connector/latest/database-execute-bulk).

## 5. Query pagination challenge

Extend Select with limit/offset input parameters. Validate that limit is bounded, offset is non-negative, and choose an allowlisted sort field if sorting is configurable. Binding SQL values is different from safely constructing SQL identifiers.

## 6. Additional operation exploration

After CRUD works, create separate test flows in a non-production schema for:
- Stored Procedure with input/output parameters.
- Execute DDL to create a scratch table.
- Execute Script with the script semantics documented for your connector version.
- Bulk Update and Bulk Delete using a small disposable dataset.
- A transaction spanning more than one database operation.

Never experiment with DDL or broad Delete statements on a production schema.
