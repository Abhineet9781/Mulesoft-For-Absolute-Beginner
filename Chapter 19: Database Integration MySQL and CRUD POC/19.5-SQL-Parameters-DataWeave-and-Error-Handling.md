# 19.5 — SQL Parameters, DataWeave Mapping, and Error Handling

## 1. Separate SQL structure from values

A database operation contains SQL and input parameters. Keep the SQL statement stable and bind data values separately.

~~~mermaid
flowchart LR
    A[HTTP JSON payload] --> B[Validate required fields]
    B --> C[DataWeave parameter object]
    C --> D[Parameterized SQL]
    D --> E[(MySQL)]
~~~

## 2. Sample Insert input mapping

Request JSON:

~~~json
{
  "firstName": "Asha",
  "lastName": "Sharma",
  "email": "asha.sharma@example.test",
  "department": "Engineering",
  "salary": 85000.00
}
~~~

Input-parameters expression:

~~~dataweave
#[{
  firstName: payload.firstName,
  lastName: payload.lastName,
  email: payload.email,
  department: payload.department,
  salary: payload.salary
}]
~~~

SQL:

~~~sql
INSERT INTO employees
(first_name, last_name, email, department, salary)
VALUES (:firstName, :lastName, :email, :department, :salary)
~~~

Named placeholders in the SQL are mapped to keys of the parameter object. Keep placeholder names consistent.

## 3. Shape a database row into API JSON

Database columns may use snake_case while the API contract uses camelCase:

~~~dataweave
%dw 2.0
output application/json
---
{
  id: payload.id,
  firstName: payload.first_name,
  lastName: payload.last_name,
  email: payload.email,
  department: payload.department,
  salary: payload.salary
}
~~~

A Select returns a collection of rows, so shape each row:

~~~dataweave
%dw 2.0
output application/json
---
payload map (row) -> {
  id: row.id,
  firstName: row.first_name,
  lastName: row.last_name,
  email: row.email,
  department: row.department,
  salary: row.salary
}
~~~

Use Transform Message after the DB operation if you need a stable public shape. The connector result type is not always identical to your intended JSON contract.

## 4. Validation before database access

Validate required fields, string lengths, allowed values, and numeric ranges before calling the database. The schema's NOT NULL and UNIQUE constraints are still important—they enforce integrity even when a request bypasses Mule.

An example conceptual request validation:

~~~text
POST /api/employees
  -> validate JSON object
  -> require firstName, lastName, email, department, salary
  -> validate salary >= 0
  -> check/handle email uniqueness
  -> Database Connector Insert
  -> respond 201 Created
~~~

Avoid a check-then-insert race as the only uniqueness control. Keep the unique database constraint and map duplicate-key failures into a deliberate response.

## 5. Error mapping

~~~mermaid
flowchart TD
    A[Database operation] --> B{Outcome}
    B -->|rows found| C[200 with mapped data]
    B -->|no row for requested ID| D[404 Not Found]
    B -->|validation failure| E[400 Bad Request]
    B -->|unique email conflict| F[409 Conflict]
    B -->|connection unavailable / unexpected DB error| G[500 or 503 per API policy]
    G --> H[Log safe diagnostic details with correlation ID]
~~~

The database operation's exception types and exact error namespaces depend on the connector/runtime; identify them using Studio's error details and documentation. Do not rely on a guessed error name without checking it in the installed version.

## 6. Update/delete row counts

For an Update or Delete, inspect the connector's result/update count to determine whether any rows matched. The exact result structure depends on connector operation/driver. A safe implementation may:
- execute Update/Delete;
- inspect affected-row count from the actual output structure;
- return 200/204 if a row was changed;
- return 404 if the requested ID matched no row;
- test how MySQL treats updating a row to identical values.

Do not assume every update count equals "rows matched" rather than "rows changed" without verifying driver settings and behavior.

## 7. SQL injection and dynamic queries

Parameterized values:

~~~sql
SELECT id, first_name, last_name
FROM employees
WHERE email = :email;
~~~

Safe input parameters:

~~~dataweave
#[{ email: attributes.queryParams.email }]
~~~

Never construct the SQL text by joining a query parameter into the query. If choosing sort direction/column dynamically is required, validate against a closed allowlist and use fixed query templates.
