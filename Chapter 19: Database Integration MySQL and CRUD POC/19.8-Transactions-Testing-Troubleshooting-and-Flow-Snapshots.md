# 19.8 — Transactions, Testing, Troubleshooting, and Flow Snapshots

## 1. Transaction basics

A transaction groups operations under a commit/rollback boundary. If a business change requires multiple related database writes to succeed together, a transaction can prevent the first write from remaining committed when the second fails. Actual semantics depend on the database, transaction manager, connector configuration, and whether operations share the same transaction-capable connection.

~~~mermaid
sequenceDiagram
    participant Mule as Mule flow / Try scope
    participant DB as Database Connector
    participant SQL as MySQL
    Mule->>DB: Begin or join transaction
    DB->>SQL: INSERT employee
    SQL-->>DB: Success
    Mule->>DB: INSERT audit row (example)
    DB->>SQL: Audit insert fails
    SQL-->>DB: Error
    DB-->>Mule: Exception
    Mule->>SQL: Rollback transaction
    Note over SQL: No partial business change if both operations share the transaction
~~~

For MuleSoft-specific syntax and supported transaction types, follow [Database Connector transaction documentation](https://docs.mulesoft.com/db-connector/latest/database-transactions). Do not add a transaction scope mechanically to every single Select.

## 2. Connection pooling and reconnection

- **Pooling** reuses established JDBC connections rather than creating a new physical connection for every operation.
- **Reconnection strategy** controls retry behavior when connecting or connectivity checks fail; it does not repair an incorrect password, missing grant, or unreachable database.
- **Timeouts** should be set with the expected network/database latency in mind.
- **Least privilege** is still required when connection pooling is enabled.
- **Secrets and TLS** must be configured for the target deployment. Localhost development settings are not deployment settings.

## 4. Testing matrix

| Test | Expected behavior |
|---|---|
| Database config valid | Test Connection succeeds |
| Wrong password | Deployment/test fails predictably; no secret returned to client |
| Create valid employee | Row inserted; API returns success |
| Create duplicate email | Unique constraint enforced; map to 409 |
| List employees | JSON array with expected fields |
| Get existing ID | One mapped record |
| Get non-existent ID | 404 according to API contract |
| Update existing ID | Row changes |
| Update invalid ID/body | 400 or 404 as appropriate |
| Delete a test row | Only the selected ID removed |
| Search department | Only matching rows returned |
| Bulk import multiple rows | Expected records committed |
| Bulk import contains duplicate | Error/rollback behavior matches explicitly tested transaction policy |
| MySQL stopped during request | Safe 5xx and server-side diagnostic log |
| SQL contains quote characters | Query remains correctly parameterized |
| Database returns DECIMAL | API numeric representation follows documented contract |

## 5. Troubleshooting

| Symptom | Common checks |
|---|---|
| Connection refused | MySQL service, port, firewall, DNS/container routing |
| Access denied | User/password, host pattern, GRANT permissions |
| Unknown database/table | Schema name, selected database, migration status |
| No suitable driver | Driver version/dependency visibility |
| SQL syntax error | MySQL dialect, placeholders, commas, reserved words |
| Parameter not found | Named SQL placeholders and DataWeave key names match |
| Wrong data types | Database column type, JDBC conversion, DataWeave output |
| Select gives empty list | Parameter value, schema/database, actual test rows |
| Duplicate key error | Unique constraints and input validation |
| Get-by-ID returns unexpected shape | Query Single result shape and no-row behavior |
| Bulk partly succeeded | Driver semantics, transaction boundary, rollback test |
| Works on laptop but fails deployed | Network access, allowlists, environment properties, TLS, secrets |
| Slow under load | Query plan/indexes, pool sizing, query timeout, payload/row count |

## 6. Observability and data safety

Log request correlation IDs, operation names, elapsed time, row counts, and sanitized error categories. Avoid writing passwords, connection strings, raw employee records, or sensitive database error details to logs or HTTP responses.

## 7. Evidence checklist for real screenshots
