# 19.9 — Practice Set, Interview Questions, and Capstone

## Part A — Core knowledge questions

1. Explain JDBC and its role in Mule Database Connector.
2. Walk through creating a Database Config for MySQL in Anypoint Studio.
3. What must be configured to make the JDBC driver available to Mule?
4. Explain the difference between MySQL Connection and Generic Connection.
5. Compare Select and Query Single.
6. What does Insert return, and how could you obtain a generated key?
7. Explain the Database Connector Update and Delete operations.
8. When should you use Bulk Insert/Update/Delete?
9. What is the purpose of Stored Procedure, Execute DDL, and Execute Script?
10. Explain how a database source differs from a processor operation.
11. What is a transaction? Explain commit and rollback.
12. What is connection pooling and what trade-offs should you consider?
13. Why are parameterized SQL statements safer than concatenated query strings?
14. What is the purpose of database uniqueness and foreign-key constraints if Mule validates input?
15. How would you map SQL error conditions to HTTP responses without exposing internals?

## Part B — Implementation challenges

### Challenge 1: Add a field

Add `job_title` to the employees table and expose it in API responses. Explain the migration plan and how older records are handled.

### Challenge 2: Pagination

Support `GET /api/employees?limit=20&offset=0`. Enforce a maximum limit and non-negative offset. Add a deterministic sort order.

### Challenge 3: Email search

Create `GET /api/employees/by-email?email=...` using a parameterized query. Decide how zero and multiple matches should be handled.

### Challenge 4: Department filter

Add department and optional minimum salary filters. Convert and validate numeric values safely.

### Challenge 5: Bulk update

Allow updating a permitted subset of employee fields for multiple records. Validate each record and use a transaction if the contract requires all-or-nothing behavior.

### Challenge 6: Stored procedure

Create a local stored procedure that returns employees by department, call it from Mule's Stored Procedure operation, and map its result to JSON. Consult version-specific parameter mapping documentation.

### Challenge 7: Transaction proof

Create a flow with two database writes and deliberately fail the second write in a disposable schema. Demonstrate that the first write rolls back when the operations share a valid transaction.

### Challenge 8: Error contract

Standardize errors to a response such as:

~~~json
{
  "errorCode": "EMPLOYEE_NOT_FOUND",
  "message": "No employee exists for the supplied ID",
  "correlationId": "example-correlation-id"
}
~~~

The correlation ID must come from your actual request/observability strategy; do not hardcode one for production.

### Challenge 9: Bulk import report

Process a list of employees and design a clear outcome for partial invalid rows. Choose explicitly between all-or-nothing and per-record success/report behavior, then implement the corresponding transactional or non-transactional strategy.

### Challenge 10: Production readiness review

Document how you would secure credentials, restrict network access, configure TLS where required, size the connection pool, set timeouts, manage schema migrations, audit sensitive reads/writes, and monitor database latency.

## Part C — Capstone: Employee Management API

Build the full POC independently:

- MySQL database and restricted application user.
- Database Config verified using Test Connection.
- POST to create employees.
- GET to list employees.
- GET by ID.
- PUT by ID.
- DELETE by ID.
- Search by department.
- Bulk insert route.
- Parameterized SQL for every user-supplied value.
- Predictable 400, 404, 409, and safe 5xx error responses.
- Transformation between API camelCase and DB snake_case.
- Tests for duplicate emails, malformed values, missing records, connection failures, and bulk failure/rollback.
- Real Studio screenshots and Postman/curl examples.
- No secrets or real employee data in Git.

### Capstone architecture

~~~mermaid
flowchart TD
    A[API Consumer] --> B[HTTP Listener /api/employees]
    B --> C[Request validation]
    C --> D{HTTP method + route}
    D -->|POST| E[Insert]
    D -->|GET| F[Select / Query Single]
    D -->|PUT| G[Update]
    D -->|DELETE| H[Delete]
    D -->|Bulk POST| I[Bulk Insert]
    E --> J[(MySQL)]
    F --> J
    G --> J
    H --> J
    I --> J
    J --> K[Map DB results to API JSON]
    K --> L[HTTP response]
    C -. validation issue .-> M[400]
    E -. unique constraint .-> N[409]
    F -. no matching row .-> O[404]
    J -. operational error .-> P[Safe 5xx + diagnostic log]
~~~
