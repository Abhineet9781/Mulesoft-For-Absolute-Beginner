# 17.7 — API-Led Practice Set and Independent Challenges

Use these exercises after completing both POCs. The first 10 are short practice checks; the remaining 10 are implementation challenges. Keep the architecture layered and test each API independently.

## Part A — 10 practice checks

1. **Identify the layer:** A mobile app needs the field `displayName` instead of `firstName` and `lastName`. Which layer should own that channel-specific shape?
2. **Identify the layer:** A database changes from PostgreSQL to Salesforce. Which API should hide the source-specific access details from its consumers?
3. **Identify the layer:** A customer record and order total must be combined for multiple consumers. Where should the shared orchestration live?
4. **RAML concept:** Does a RAML response example cause Mule to return that response automatically? Explain.
5. **APIkit concept:** What does the APIkit Router do, and what business logic must you still implement?
6. **HTTP concept:** Why is `200 OK` with `{"code":"NOT_FOUND"}` a poor substitute for a true 404 response?
7. **Dependency failure:** How should the Process API distinguish an unknown customer from an unavailable System API?
8. **Contract drift:** Name three things to compare between the RAML contract and the running application.
9. **Testing:** Why should you test System and Process APIs independently before end-to-end testing?
10. **Security:** Why should you not expose backend credentials or raw exception messages in the Experience API response?

Write a short answer for each. Use the previous chapters and official documentation to verify your reasoning.

## Part B — 10 implementation challenges

### Challenge 1 — Add a customer

Add `C-300` with a new name and status. Acceptance criteria: direct System API and end-to-end Experience API both return the new customer.

### Challenge 2 — Add a customer status rule

If a customer is `INACTIVE`, return `membershipStatus: "INACTIVE"` without changing the System API source fields. Acceptance criteria: the mapping works for both ACTIVE and INACTIVE samples.

### Challenge 3 — Add query filtering

Add optional query parameter `includeEmail` to the Experience API. If false, omit the email field; if true or absent, include it. Update the RAML contract in POC 1 and manual documentation in POC 2.

### Challenge 4 — Introduce a stable error schema

Return `code`, `message`, and `correlationId` for not-found and upstream errors. Acceptance criteria: the HTTP status distinguishes 404 from 502/503/504 as appropriate.

### Challenge 5 — Make the order summary data-driven

Replace hardcoded order count/value with a separate Order System API on a new port. Acceptance criteria: Process API calls both Customer and Order System APIs and composes the result.

### Challenge 6 — Add pagination

Create a `GET /customers` route with `limit` and `offset`. Document bounds and defaults. Acceptance criteria: invalid values produce a clear client error and valid values return pagination metadata.

### Challenge 7 — Add correlation IDs

Accept an inbound correlation ID or create one if absent, then pass it to downstream calls and include it in the response metadata. Do not log sensitive payloads.

### Challenge 8 — Add timeout handling

Stop the System API and observe the Process API behavior. Add a controlled timeout/error response. Acceptance criteria: no false 404 and no leaked stack trace.

### Challenge 9 — Add automated tests

Write MUnit tests for the success transform, not-found mapping, and downstream failure. Acceptance criteria: tests assert both body and status semantics.

### Challenge 10 — Add a second Experience API

Create a partner-facing response with different field names but reuse the same Process API. Acceptance criteria: the two Experience APIs have different contracts but share the business orchestration.

## Part C — Review rubric

| RAML/APIkit POC works | /2 |
| No-RAML POC works | /2 |
| DataWeave mapping is readable and robust | /2 |
| Tests cover success and failure cases | /2 |
| No secrets or sensitive payloads in logs | /2 |
| Can explain the trade-offs | /2 |
| **Total** | **/20** |

A score of 16 or above is a useful target, provided the two POCs actually run and you can explain the choices. Do not award yourself points for a diagram or code that has not been executed.
