# 17.3 — POC 1: Import RAML into Anypoint Studio with APIkit

In this lesson, turn the Experience API contract from 17.2 into a Mule application scaffold. APIkit uses the API specification to create routing and supporting configuration; you still implement the integration logic.

## 1. Create the APIkit project

The exact wizard wording can vary by Anypoint Studio release, but the workflow is:

1. Open Anypoint Studio.
2. Choose **File → New → Mule Project** (or the equivalent new Mule project action).
3. Name the project `customer-experience-api`.
4. Choose a Mule 4 runtime supported by your Studio installation.
5. Select the option to create/import a project from an API specification or RAML, if offered.
6. Choose the local `customer-experience-api.raml` created in 17.2. If the wizard offers Design Center/Exchange import instead, select the spec only if it is already published there and you have access.
7. Complete the wizard and inspect the generated configuration.

If your Studio version does not offer RAML import in the initial wizard, create a Mule project and use the APIkit REST scaffolding/import action provided by that version. Follow the current APIkit documentation rather than assuming every Studio release has identical menus.

## 2. What APIkit generates

Expect APIkit configuration and a main flow containing an APIkit Router, plus resource/method implementation flows. The exact XML and flow names are generated from the contract and can vary.

Conceptually:

```mermaid
flowchart TD
  H[HTTP Listener] --> R[APIkit Router]
  R --> G[GET /customers/{customerId}/summary flow]
  G --> B[Experience mapping and HTTP Request to Process API]
  B --> O[JSON response]
```

The router matches the incoming path/method against the RAML contract and dispatches to the relevant implementation flow. It is not the Process API and should not directly access a database in this architecture.

## 3. Configure the inbound listener

Configure the app's HTTP Listener to use port `8083`. Depending on the generated scaffold, the listener path may be `/api/*` or a configured base path that includes the RAML base path. Avoid duplicating `/api`: check the generated listener path and APIkit configuration before testing.

If the generated project uses an HTTP Listener configuration global, give it a clear name such as `HTTP_Listener_config`. Use `localhost` for the host in a local-only lab.

## 4. Implement the generated resource flow

Open the generated flow for `GET /customers/{customerId}/summary`. Add an HTTP Request operation to call the Process API:

- Host: `localhost`
- Port: `8082`
- Method: `GET`
- Path: `/api/customer-summary/` followed by the incoming `customerId` URI parameter.
- Response: preserve the Process API's JSON payload or transform it into the Experience API contract.

Use the URI parameter available in the event attributes. The precise expression path depends on the generated APIkit configuration and Mule runtime metadata; inspect the event in Studio rather than copying an assumed path blindly. In APIkit-generated flows, URI parameters are commonly exposed through listener/APIkit attributes. Confirm whether your project uses `attributes.uriParams.customerId` or another generated variable/context before running.

For this lab, the Experience mapping should produce:

```dataweave
%dw 2.0
output application/json
---
{
  id: payload.customer.customerId,
  name: payload.customer.firstName ++ " " ++ payload.customer.lastName,
  email: payload.customer.email,
  membershipStatus: payload.customer.status,
  orderSummary: {
    orderCount: payload.orders.count,
    totalValue: payload.orders.totalValue,
    currency: payload.orders.currency
  }
}
```

This mapping assumes the Process API returns the structure documented in 17.1. If your Process API returns a different shape, align the mapping or the Process API contract; do not mask a mismatch with arbitrary defaults.

## 5. Error behavior

Implement a not-found path so an unknown customer becomes HTTP 404 with the `ApiError` body documented in RAML. Do not return HTTP 200 with an error-shaped JSON object. If the Process API propagates a 404, map or preserve it deliberately and verify the actual status at the Experience API.

APIkit can help route requests and handle invalid API requests according to its configuration, but business errors still need deliberate implementation.

## 6. Build and run

1. Save the project and resolve XML/configuration errors.
2. Start System API and Process API after completing their implementations in 17.4.
3. Run `customer-experience-api`.
4. Watch the Console for deployment errors.
5. Test only after the other two dependencies are listening.

Do not assume the generated scaffold is fully implemented merely because the project compiles.

## 7. Troubleshooting

| Symptom | Check |
|---|---|
| APIkit cannot parse the spec | RAML header, indentation, type definitions, and parser error location |
| 404 for every path | Listener path, base path, APIkit configuration, HTTP method, and generated flow |
| Duplicate `/api/api` | Listener path and RAML base URI are both adding the base path |
| Router dispatch error | Request method/path does not match the contract or generated flow |
| Process API connection refused | Process API is not running or wrong port/host |
| Payload selector fails | Actual Process API response shape differs from the mapping assumptions |
| HTTP status is wrong | Configure response status deliberately and inspect error-handler behavior |

## 8. Completion criteria

- [ ] RAML imports and APIkit scaffolding is generated.
- [ ] You can point out the APIkit Router and generated GET implementation flow.
- [ ] The generated Experience flow calls Process API, not System API directly.
- [ ] The response matches the RAML success shape.
- [ ] Unknown IDs return the documented 404 behavior.
