# 18.3 — JSON to CSV: End-to-End Download API

## Objective

Create POST /transform/json-to-csv. The client sends a JSON array; Mule selects a stable set and order of columns, serializes it as CSV, and responds as a downloadable file.

## Flow snapshot — Studio canvas

~~~mermaid
flowchart TD
    A[HTTP Listener: POST /transform/json-to-csv] --> B[Transform Message: JSON array to CSV]
    B --> C[Set response headers]
    C --> D[HTTP response body is CSV text]
    B -. invalid JSON or schema .-> E[Error Handler]
    E --> F[400 Bad Request]
~~~

## Request

~~~http
POST http://localhost:8081/transform/json-to-csv
Content-Type: application/json
Accept: text/csv

[
  {"employeeId":"E001","firstName":"Asha","department":"Engineering","salary":85000},
  {"employeeId":"E002","firstName":"Ravi","department":"Finance","salary":72000}
]
~~~

## DataWeave — JSON to CSV

~~~dataweave
%dw 2.0
input payload application/json
output application/csv header=true, separator=",", quoteValues=true
---
payload map (row) -> {
  employeeId: row.employeeId,
  firstName: row.firstName,
  department: row.department,
  salary: row.salary
}
~~~

Expected body:

~~~csv
employeeId,firstName,department,salary
E001,Asha,Engineering,85000
E002,Ravi,Finance,72000
~~~

CSV output is text. For an HTTP client, set the response media type appropriate for your API contract, commonly text/csv; charset=UTF-8, and a download filename through Content-Disposition: attachment; filename="employees.csv".

## Response headers

In the Listener response configuration, use a response header expression similar to:

~~~dataweave
#[{
  "Content-Type": "text/csv; charset=UTF-8",
  "Content-Disposition": "attachment; filename=\"employees.csv\""
}]
~~~

Check the exact expression editor and header UI in your Studio version. The body must contain CSV text and the headers must describe it accurately.

## Mule flow outline

~~~text
HTTP Listener (POST /transform/json-to-csv)
  -> Transform Message (JSON -> CSV)
  -> HTTP Listener response returns transformed payload
~~~

No File Write is needed unless the requirement includes saving a server-side copy.

## Test

~~~bash
curl -i -X POST "http://localhost:8081/transform/json-to-csv"   -H "Content-Type: application/json"   -H "Accept: text/csv"   --data '[{"employeeId":"E001","firstName":"Asha","department":"Engineering","salary":85000}]'
~~~

Save to a file:

~~~bash
curl -sS -X POST "http://localhost:8081/transform/json-to-csv"   -H "Content-Type: application/json"   --data-binary @employees.json -o employees.csv
~~~

## Important design points

- Choose output columns explicitly so schema changes don't unexpectedly alter the export contract.
- Decide how nulls and missing values appear in CSV.
- Configure quoting and separator for the downstream system.
- Use the CSV writer rather than manually concatenating rows. CSV escaping is subtle.
- For large inputs, assess memory use and streaming; mapping a complete array is not constant-memory.

## Practice questions

1. Why specify output columns explicitly?
2. Which header tells browsers to treat a response as an attachment?
3. What can go wrong if CSV rows are manually concatenated with string operations?
4. How should an empty value differ from a missing value in the export contract?
5. How would you create a CSV containing only employeeId and department?
6. What changes if the incoming JSON is one object instead of an array?

## Mini challenge

Add an optional fields query parameter such as fields=employeeId,department. Validate it against an allowlist before selecting output fields. Never allow arbitrary user-supplied expressions.
