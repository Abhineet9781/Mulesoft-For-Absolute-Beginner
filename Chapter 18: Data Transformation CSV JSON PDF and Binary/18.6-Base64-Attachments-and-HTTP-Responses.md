# 18.6 — Base64, Attachments, HTTP Headers, and Safe Binary Delivery

## 1. Raw binary vs Base64

Raw binary is a file's actual byte sequence. Base64 represents those bytes with text characters, allowing them to be carried in JSON or other text-oriented envelopes. Base64 generally increases size and must be decoded before the result is treated as a file.

~~~mermaid
flowchart LR
    A[Original PDF bytes] --> B[Base64 encoder]
    B --> C[JSON string field containing Base64]
    C --> D[Base64 decoder]
    D --> E[Original byte sequence]
~~~

Base64 decode does not validate that the bytes are a safe PDF, and it does not extract document text.

## 2. DataWeave examples

DataWeave versions provide Base64 functions through core modules. Confirm the exact function signature in the DataWeave runtime used by your app. A common pattern is:

~~~dataweave
%dw 2.0
import * from dw::core::Binaries
output application/json
---
{
  encoded: toBase64(payload as Binary)
}
~~~

Decode a Base64 string into binary:

~~~dataweave
%dw 2.0
import * from dw::core::Binaries
output application/octet-stream
---
fromBase64(payload.encoded)
~~~

Treat these as script templates to validate in Studio for your runtime version. The JSON field must be a string and should be validated against size/input requirements before decoding.

## 3. HTTP response headers

- Content-Type describes the response body's media type.
- Content-Disposition: attachment; filename="report.pdf" asks typical browsers to download the body using the suggested filename.
- Content-Length gives byte length when known; do not hardcode it unless it matches the actual bytes.
- Streaming or chunked transfer framing does not change the file format.

Known PDF response:

~~~text
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
~~~

Generic binary response:

~~~text
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="download.bin"
~~~

A suggested filename is not a trusted filesystem path. Sanitize upload names and prevent path traversal.

## 4. Flow snapshot — Base64 JSON to binary download

~~~mermaid
flowchart TD
    A[HTTP Listener: POST /files/decode] --> B[Validate JSON and Base64 field]
    B --> C[DataWeave fromBase64]
    C --> D[Binary payload]
    D --> E[HTTP response: PDF or octet-stream]
    B -. invalid input .-> F[400 response]
~~~

Do not claim output is a PDF just because the request says so. Define allowed formats in the API contract and use safe format-aware validation when needed.

## 5. Multipart/form-data

Multipart requests contain boundaries, form fields, and file parts. Do not Base64-decode the entire multipart payload as if it were one Base64 string. Configure the API for the multipart contract, select the file part, then work with that part's content.

## Mini lab

Create POST /files/encode to accept raw bytes and return JSON with a Base64 string. Create POST /files/decode to accept this JSON and return the original bytes. Compare the downloaded file with the source. Start with a small text file, then use a small sample PDF. Do not use confidential documents.
