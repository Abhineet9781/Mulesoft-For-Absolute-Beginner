# 18.2 — CSV to JSON: End-to-End HTTP API

## Objective

Create POST /transform/csv-to-json. The client sends CSV text in the HTTP request body. Mule parses each CSV record and returns JSON.

## Flow snapshot — Studio canvas

~~~mermaid
flowchart TD
    A[HTTP Listener: POST /transform/csv-to-json] --> B[Transform Message]
    B --> C[Logger: status and record count only]
    C --> D[HTTP Response: 200 + application/json]
    B -. parse or cast fails .-> E[Error Handler]
    E --> F[400 Bad Request: safe error body]
~~~

**Studio configuration**

- Create an HTTP Listener global configuration with host 0.0.0.0 and port 8081.
- Listener path: /transform/csv-to-json; method: POST.
- Set or verify that the CSV reader sees application/csv. For a learning endpoint, use a declared CSV input format if Studio cannot infer it.
- Output directive: application/json.
- Configure errors deliberately; malformed CSV or invalid domain data should not accidentally return HTTP 200.

## Sample request

~~~http
POST http://localhost:8081/transform/csv-to-json
Content-Type: application/csv
Accept: application/json

employeeId,firstName,department,salary
E001,Asha,Engineering,85000
E002,Ravi,Finance,72000
~~~

## DataWeave — CSV to JSON

Use this in Transform Message. Ensure the component input metadata or incoming media type is configured as CSV.

~~~dataweave
%dw 2.0
input payload application/csv
output application/json
---
payload map (row) -> {
  employeeId: row.employeeId,
  firstName: row.firstName,
  department: row.department,
  salary: row.salary as Number
}
~~~

Expected response:

~~~json
[
  {
    "employeeId": "E001",
    "firstName": "Asha",
    "department": "Engineering",
    "salary": 85000
  },
  {
    "employeeId": "E002",
    "firstName": "Ravi",
    "department": "Finance",
    "salary": 72000
  }
]
~~~

Employee IDs remain strings while salary is explicitly converted to a number.

## Mule XML teaching template

This is a schematic XML template. Use Studio's configuration editor to create the HTTP Listener, Transform Message, global configuration, namespaces, and response settings for your connector version.

~~~xml
<flow name="csv-to-json-flow">
    <http:listener config-ref="HTTP_Listener_config"
                   path="/transform/csv-to-json"
                   allowedMethods="POST"/>
    <ee:transform doc:name="CSV to JSON">
        <ee:message>
            <ee:set-payload><![CDATA[
%dw 2.0
input payload application/csv
output application/json
---
payload map (row) -> {
  employeeId: row.employeeId,
  firstName: row.firstName,
  department: row.department,
  salary: row.salary as Number
}
            ]]></ee:set-payload>
        </ee:message>
    </ee:transform>
</flow>
~~~

Do not paste this fragment into an empty XML file and expect it to run without the proper Mule, HTTP, and EE namespaces and global configuration. Studio can generate those declarations.

## Test with curl

~~~bash
curl -i -X POST "http://localhost:8081/transform/csv-to-json"   -H "Content-Type: application/csv"   -H "Accept: application/json"   --data-binary @employees.csv
~~~

Expected: HTTP 200, a JSON array, and Content-Type application/json.

## Negative tests

- Missing required header row.
- Empty CSV body.
- Salary contains unknown instead of a number.
- A field contains a comma inside quotes, such as "Research, Development".
- Malformed quote escaping.
- A header uses employee_id instead of employeeId.

Validate required headers and values, then map parsing/validation errors to an appropriate 4xx response without exposing internal exception details.

## Practice questions

1. Why should employeeId stay a string?
2. What does the CSV reader return for each record?
3. What changes if CSV has no header?
4. How would you filter rows with salary greater than 80,000?
5. How would you handle blank salary safely?
6. Which component creates the outbound JSON representation?
7. Why is setting only the output header not enough to parse CSV?
