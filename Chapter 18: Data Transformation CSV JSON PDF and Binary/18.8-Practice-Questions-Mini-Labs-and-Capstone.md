# 18.8 — Practice Questions, Mini Labs, and Capstone

## How to use this practice set

Try every task yourself in Anypoint Studio before reading external examples. Save your DataWeave scripts, request samples, expected responses, and screenshots of your own running flows. These challenges deliberately require both transformation logic and Mule flow configuration.

## Part A — Concept questions

Answer in your own words.

1. Explain the roles of the DataWeave reader, mapping script, and writer.
2. Distinguish a DataWeave format ID from an HTTP MIME type.
3. Why are CSV values commonly exposed as strings?
4. What is the risk of converting an identifier such as 00042 to a number?
5. Why should CSV be serialized with a CSV writer instead of by concatenating strings?
6. Explain header=true and header=false for CSV.
7. What is the difference between application/pdf and application/octet-stream?
8. Why doesn't reading a PDF into Mule automatically extract its text?
9. Does Base64 encrypt a file? Does it change its underlying document format?
10. Explain Content-Type and Content-Disposition.
11. Why are actual binary bytes different from a Base64 string?
12. What does streaming aim to improve, and what does it not guarantee?
13. Why should a transform be tested with empty, malformed, and oversized inputs?
14. Why should IDs and phone numbers often remain strings?
15. How can response headers be wrong even when the DataWeave output is right?

## Part B — DataWeave implementation drills

### Task 1 — CSV to JSON with type conversion

Input:

~~~csv
orderId,quantity,unitPrice
ORD-001,2,120.50
ORD-002,1,45.00
~~~

Requirements:
- Keep orderId as a string.
- Convert quantity and unitPrice to numeric values.
- Add lineTotal = quantity * unitPrice.
- Return JSON with stable field names.
- Define behavior for invalid or blank numeric input.

### Task 2 — JSON to CSV with selected fields

Input:

~~~json
[
  {"id":"P-01","name":"Keyboard","category":"Accessories","price":1599,"internalNote":"Do not export"},
  {"id":"P-02","name":"Mouse","category":"Accessories","price":799,"internalNote":"Internal"}
]
~~~

Requirements:
- Export only id, name, category, price.
- Include a header.
- Keep the order exactly as requested.
- Ensure internalNote never appears in the CSV.
- Test a name containing a comma.

### Task 3 — Normalize CSV fields

Input has inconsistent casing and spaces in customer names and email addresses.

Requirements:
- Trim whitespace.
- Normalize email casing if the business rules permit it.
- Preserve the original customer identifier.
- Skip or reject rows with a missing required identifier.
- Explain why trimming does not replace validation.

### Task 4 — Group and summarize

Read CSV transaction rows and produce JSON grouped by department with transaction count and total amount. Define what happens when an amount is invalid.

### Task 5 — JSON to CSV with nulls

Design a consistent policy for missing versus null fields. Implement it and show a sample CSV output.

### Task 6 — Validate an API request

Create POST /transform/csv-to-json. Reject unsupported request content types and empty bodies. Return a controlled error for malformed CSV and invalid domain values.

## Part C — Mule flow mini labs

### Lab 1 — CSV to JSON endpoint

Build POST /transform/csv-to-json on local port 8081.
- Reader: CSV.
- Output: JSON.
- Test through Postman and curl.
- Add a validation/error path.
- Save a screenshot of the running Studio canvas and one successful request.

Acceptance criteria: correct row count, proper numeric types where required, correct response media type, and predictable error behavior.

### Lab 2 — JSON to CSV download

Build POST /transform/json-to-csv.
- Accept a JSON array.
- Select explicit output columns.
- Return CSV as the response body.
- Set response media type and Content-Disposition for a file download.
- Confirm the saved file opens correctly in a spreadsheet editor or text editor.

Acceptance criteria: stable header/column order, proper quoting, no unexpected extra fields, and correct download filename.

### Lab 3 — File-based conversion

Read employees.csv, convert rows to JSON, and write a JSON file.
- Use environment-safe paths.
- Avoid overwriting previous results without an explicit policy.
- Handle file-not-found and write-permission failures.
- Test an empty and malformed input.

Acceptance criteria: valid output file, error behavior documented, and no sensitive payloads in logs.

### Lab 4 — PDF pass-through

Create GET /files/sample.pdf.
- Read a small test PDF from a safe location.
- Return its binary bytes without string conversion.
- Set application/pdf.
- Save the response using curl and open the downloaded file.

Acceptance criteria: file opens, body bytes are preserved, and headers describe the response accurately.

### Lab 5 — Base64 round trip

Build an encode endpoint and a decode endpoint.
- Encode binary bytes into Base64 in JSON.
- Decode the Base64 field into binary.
- Apply request and decoded-size limits.
- Compare output file with original by byte length or a hash.
- Test invalid Base64.

Acceptance criteria: round-trip bytes match and invalid input is rejected safely.

## Part D — Capstone: Employee Export Service

### Business scenario

An HR system provides employee records as CSV. A consumer submits the CSV to Mule and wants a normalized JSON response. A separate route accepts validated JSON records and returns a downloadable CSV export. An administrator can retrieve a sample PDF policy document unchanged.

### Architecture

~~~mermaid
flowchart TD
    A[Consumer] --> B{Route}
    B --> C[POST /employees/import]
    C --> D[CSV reader]
    D --> E[Validate and normalize rows]
    E --> F[JSON response]
    B --> G[POST /employees/export]
    G --> H[Validate JSON array]
    H --> I[Transform to CSV]
    I --> J[Download response]
    B --> K[GET /documents/policy]
    K --> L[Read PDF bytes]
    L --> M[Binary PDF response]
~~~

### Required endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | /employees/import | CSV → normalized JSON |
| POST | /employees/export | JSON array → CSV download |
| GET | /documents/policy | Pass through a PDF file |

### Requirements

- Use consistent response/error schemas for validation failures.
- Keep employee identifiers as strings.
- Convert numeric fields only after validation.
- Define treatment of unknown CSV headers, duplicate rows, blank values, and malformed input.
- Use CSV writer quoting options instead of manual string assembly.
- Set accurate content types and download headers.
- Preserve the policy PDF bytes.
- Avoid logging full employee records or document content.
- Write test evidence for happy paths and failure cases.
- Explain what additional security, authentication, deployment, monitoring, and file-retention controls a production version would require.

### Capstone grading rubric

| Category | Points |
|---|---:|
| CSV parsing and JSON mapping | 20 |
| JSON to CSV output and download headers | 20 |
| Binary/PDF pass-through correctness | 15 |
| Validation and error handling | 15 |
| Testing: happy path, edge cases, negative cases | 15 |
| Flow design, diagrams, and documentation | 10 |
| Security and operational reasoning | 5 |
| **Total** | **100** |

Suggested self-assessment: 90–100 = strong and well-tested; 75–89 = working with gaps; 60–74 = revisit transformation and edge-case handling; below 60 = repeat Labs 1–3 before continuing.

## Interview-style questions

1. A downstream system returns CSV but an upstream REST API expects JSON. Where would you put the mapping and what metadata must be correct?
2. The output is valid JSON but the client sees it as a download with a .csv filename. What would you inspect?
3. Your CSV has 0015 in an employee ID column. How do you preserve it?
4. A PDF reaches the downstream system but will not open. What checks would you perform to determine where bytes changed?
5. The API accepts a 10 MB Base64 string that decodes to a much larger payload. Which limits and checks are important?
6. How would you test behavior when one row contains an invalid numeric amount?
7. What are the trade-offs between reading an entire file and streaming it?
8. Why is transforming JSON into binary not the same as generating a PDF?
9. How would you prevent malicious filenames from being used in filesystem paths?
10. What evidence would you include to show that a flow was tested in Anypoint Studio rather than only documented?
