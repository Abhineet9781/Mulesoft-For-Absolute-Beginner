# 6.3 — HTTP Request: Configuration Deep Dive

**HTTP Request** is an outbound operation. It sends an HTTP request from a Mule flow to another service or API. It is different from HTTP Listener, which receives a request and starts a flow.

> **Official configuration reference:** [HTTP Connector documentation](https://docs.mulesoft.com/http-connector/latest/http-documentation). Use it alongside this guide; exact fields depend on the HTTP Connector version installed in Studio.

## Configuration is split into two parts

1. **Global HTTP Request Configuration** — connection details shared by request operations.
2. **HTTP Request operation** — method, path, request body, headers, query parameters, and response/error behavior for a specific call.

## 1. Global HTTP Request Configuration

Create one by clicking **+** beside Connector configuration.

| Field | Meaning | Example |
|---|---|---|
| Name | Configuration name referenced by the operation | `HTTP_Request_config` |
| Protocol | HTTP or HTTPS | HTTPS for a secure public API |
| Host | Target server hostname | `postman-echo.com` |
| Port | Target port | `443` for HTTPS, commonly implied by protocol |
| Base path | Optional common URL prefix | `/api/v1` |

For example, host `postman-echo.com` with HTTPS targets that host. Do not include the scheme in the Host field when Studio has a separate Protocol field.

## 2. General tab of the Request operation

| Field | Purpose | Example |
|---|---|---|
| Connector configuration | Selects the global request config | `HTTP_Request_config` |
| Method | HTTP method to send | GET |
| Path | Resource path on the target host | `/get` |
| Body | Request body for methods/APIs that need one | JSON for a POST |
| Target / Target Value | Optional place to store response data rather than replacing the payload | `vars.apiResponse` (when using the target settings supported by your version) |

A request to `https://postman-echo.com/get` can be configured with HTTPS, host `postman-echo.com`, method GET, and path `/get`.

## 3. Parameters and headers

- **Query parameters** are URL parameters such as `?limit=10`.
- **Headers** carry metadata such as `Accept` or an authorization header.
- **URI parameters** fill path placeholders where supported by the request configuration.
- **Body** carries data for operations that accept a request body.

For JSON request bodies, ensure the payload is valid JSON. Mule usually infers the outgoing Content-Type from the payload MIME type; avoid manually overriding Content-Type without a reason, especially for multipart requests.

Never hard-code real credentials in a tutorial or commit them to Git.

## 4. Response and error handling

HTTP Request receives a response from the remote server. The response body becomes the current payload by default, and response metadata is available in attributes. If you need to preserve the original payload, configure a target variable where supported.

HTTP status codes and connectivity errors are different:
- A remote `404` means the server responded but the resource was not found.
- A connection timeout/refusal means a response may not have been received.
- A `5xx` response indicates a server-side failure or gateway condition.

Configure timeouts, retries, and error handling based on the API's reliability and idempotency. Do not retry non-idempotent operations blindly.

## XML example

```xml
<http:request-config name="HTTP_Request_config">
    <http:request-connection protocol="HTTPS" host="postman-echo.com" />
</http:request-config>

<flow name="callEchoApiFlow">
    <http:listener config-ref="HTTP_Listener_config" path="/call-echo"/>
    <http:request config-ref="HTTP_Request_config" method="GET" path="/get"/>
</flow>
```

Treat this as a simplified illustration; Studio may generate additional namespace, documentation, and connector-version attributes.

## Common mistakes

- Putting `https://` in Host when Protocol has its own field.
- Forgetting to set the request method or path.
- Confusing Listener (inbound) with Request (outbound).
- Assuming every response is HTTP 200.
- Logging credentials or sending secrets in query parameters.

## Practice

Build a flow with Listener `/call-echo` followed by HTTP Request to `https://postman-echo.com/get`. Call `http://localhost:8081/call-echo` from Postman and inspect the returned payload and attributes.
