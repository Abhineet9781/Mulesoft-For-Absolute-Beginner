# 18.7 — Testing, Troubleshooting, and Studio Flow Snapshots

## 1. Flow snapshots: reconstruct these canvases in Anypoint Studio

These Mermaid diagrams are **schematic Studio canvas snapshots**: they show the component order and branches you should build. They are not screenshots captured from a live Studio session. Actual screenshots can be added after you run the flows locally.

### Snapshot A — CSV to JSON API

~~~mermaid
flowchart TD
    subgraph Main_Flow
      A[HTTP Listener POST /transform/csv-to-json]
      B[Transform Message: CSV to JSON]
      C[Logger: success + row count]
      A --> B --> C
    end
    B -. failure .-> D[Error Handler]
    D --> E[Return 400 with safe error payload]
~~~

Suggested component checklist:
- HTTP Listener configured for POST.
- CSV reader/input MIME type established.
- Transform Message output JSON.
- Logger that avoids printing raw/large payloads.
- Error strategy with explicit HTTP response status and safe message.

### Snapshot D — Binary PDF pass-through

~~~mermaid
flowchart TD
    A[HTTP Listener] --> B[File Read or HTTP Request]
    B --> C[Preserve binary bytes]
    C --> D[Set appropriate response metadata]
    D --> E[Return PDF / octet stream]
~~~

The core rule in Snapshot D is *do not add a text-based Transform Message just to change the MIME type*. Set the response metadata correctly and preserve the bytes.

## 2. Test matrix

| Case | Input | Expected check |
|---|---|---|
| CSV happy path | Valid header and two rows | JSON array with two objects |
| CSV quoted comma | Department is "Research, Development" | One field value, not two columns |
| CSV invalid number | Salary is "unknown" | Predictable 4xx; no stack trace in response |
| CSV missing header | Header absent or wrong | Explicit header strategy or validation error |
| JSON happy path | Array of two objects | CSV header and two data rows |
| JSON fields missing | One record lacks department | Defined empty/default/error behavior |
| JSON scalar | String instead of expected array | Validation error or documented single-record behavior |
| Empty input | Empty request body | Controlled 400 response |
| Bad JSON | Malformed JSON text | Controlled parse error response |
| PDF pass-through | Small known PDF | Result opens and byte length/hash matches source |
| Unsupported binary | Random bytes sent to PDF-only route | Rejected if PDF validity is required |
| Missing file | File Read uses nonexistent path | Error handled; no misleading success |
| Read-only target | File Write target cannot be written | Error handled and observable |

## 3. curl commands

CSV to JSON:

~~~bash
curl -i -X POST "http://localhost:8081/transform/csv-to-json" \
  -H "Content-Type: application/csv" \
  -H "Accept: application/json" \
  --data-binary @employees.csv
~~~

JSON to CSV:

~~~bash
curl -sS -X POST "http://localhost:8081/transform/json-to-csv" \
  -H "Content-Type: application/json" \
  --data-binary @employees.json \
  -o employees.csv
~~~

Download a PDF while saving headers separately:

~~~bash
curl -sS -D response-headers.txt \
  "http://localhost:8081/files/sample.pdf" \
  -o sample-downloaded.pdf
~~~

## 4. Troubleshooting guide

| Symptom | Likely reason | Check |
|---|---|---|
| CSV input is treated as one long string | Reader MIME type or metadata isn't CSV | Inspect incoming media type and CSV reader config |
| CSV columns are not accessible by name | Header is disabled, missing, or different | Check the first row and header properties |
| Salary comparison behaves incorrectly | CSV values still strings | Cast only validated numeric values |
| CSV commas/quotes appear corrupted | Manual string concatenation or wrong writer options | Use the CSV writer |
| Response says JSON but body looks like CSV | Response headers and actual writer disagree | Check output directive and Listener response |
| Downloaded PDF will not open | Bytes changed, headers accidentally saved, or response was transformed | Save body only; compare size/hash; remove text transformations |
| Browser displays binary as text | Incorrect Content-Type or content-disposition contract | Inspect actual body and headers |
| PDF logs show strange characters | Binary bytes are being rendered in a text log | Do not log entire binary payload |
| Large transform runs out of memory | Full payload materialized or input too large | Review streaming, payload size, and algorithm |

## 5. What a real Studio screenshot should prove

When you add real screenshots from your own running app, include:
1. The complete canvas with component names readable.
2. The Transform Message editor showing the DataWeave script.
3. The Listener settings showing path and method.
4. Request/response results in Postman or another client.
5. Console output only where it provides meaningful evidence and contains no secrets or personal data.

Use descriptive filenames such as `chapter18-csv-to-json-canvas.png`, `chapter18-json-to-csv-transform.png`, and `chapter18-pdf-response-test.png`. Do not label a schematic diagram as an actual screenshot.

## 6. Final practice checks

1. How would you determine whether a bad response comes from reader config, mapping logic, or response headers?
2. What would you inspect first when the CSV payload becomes a string rather than an array?
3. How can you verify that a PDF pass-through did not change bytes?
4. What behavior should an API implement when a field is missing in one record but present in others?
5. Why should response headers be tested alongside payload content?
6. Which failures should be 400, 413, 415, or 500, based on your API contract?
7. What should be measured before transforming a multi-gigabyte CSV?
