# 20.8 — Certificate Lifecycle, Rotation, and Production Security

## 1. A certificate is a lifecycle, not a one-time setup

Certificate operations include:
1. Inventory the service, owner, hostname, CA, certificate serial/fingerprint, expiry, and usage.
2. Request or issue a certificate through an approved process.
3. Verify identity, SANs, key usage, chain, validity, and issuer before deployment.
4. Deploy the certificate and private key through an approved secret/certificate delivery mechanism.
5. Test the handshake from the real client/server path.
6. Monitor expiration and trust changes.
7. Renew and rotate before expiry.
8. Revoke or disable compromised credentials.
9. Remove retired keys and stale trust entries according to policy.

## 2. Rotation strategy

A safer rotation sequence often looks like this:

~~~mermaid
flowchart TD
    A[Inventory and expiry alert] --> B[Issue new certificate]
    B --> C[Validate SAN, chain, key usage, validity]
    C --> D[Distribute new trust if CA/identity changes]
    D --> E[Deploy new identity]
    E --> F[Test handshake and business request]
    F --> G{Healthy?}
    G -- No --> H[Rollback to approved prior identity]
    G -- Yes --> I[Observe during overlap window]
    I --> J[Remove old trust/key when safe]
~~~

If a leaf certificate changes under the same trusted CA, clients may not need a truststore update. If the issuer or trust anchor changes, trust distribution may need to happen before the server identity changes. Coordinate both ends and avoid removing old trust before all relevant clients have migrated.

## 3. Private-key protection

- Keep private keys out of source repositories and general-purpose logs.
- Limit who can read or export keys.
- Use secrets managers, managed key stores, HSMs, or platform-supported certificate facilities where appropriate.
- Separate development, test, staging, and production identities.
- Do not reuse one private key across unrelated services/environments without a documented reason.
- Restrict backup access and protect backups.
- Rotate immediately according to incident procedures if a private key is exposed.

## 4. Password management

Passwords should be injected through approved secure configuration or secrets management. Avoid:
- Hardcoding passwords in Mule XML.
- Committing configuration files containing plaintext passwords.
- Using one password for every environment.
- Logging resolved secure property values.
- Putting passwords directly into shell history or tickets.

Secure configuration syntax and deployment secret integration depend on the application, runtime, and deployment target. Verify the exact mechanism supported by your environment.

## 5. Truststore scope and least privilege

A truststore defines who can be trusted for a particular connection. Keep trust scopes as narrow as the business architecture reasonably permits:
- Separate truststores by partner or security boundary where appropriate.
- Prefer trusted CA roots with managed issuance policy when suitable.
- Avoid trusting broad, unrelated CAs for highly sensitive mTLS client authentication.
- Track why each certificate is present and who owns its renewal.
- Remove stale trust entries only after confirming they are no longer required.

## 6. Revocation and compromise

Certificate revocation checking behavior depends on the Java provider, runtime, TLS configuration, and infrastructure. Do not assume CRL or OCSP checking is enabled just because certificates are used. Define how compromised client identities are disabled, including application authorization changes, trust-policy changes, credential revocation, and incident communication.

For mTLS, a certificate signed by a trusted CA may still represent a compromised client. Authorization and revocation controls must support rapid disablement.

## 7. Production checklist

- [ ] TLS is required for sensitive network paths.
- [ ] Supported TLS protocol versions and cipher policy align with current organizational standards.
- [ ] Hostname verification is enabled.
- [ ] Certificates include correct SANs, key usages, and validity.
- [ ] Server presents a complete certificate chain.
- [ ] Keystores/truststores use supported formats and explicit types.
- [ ] Private keys are protected and access is least-privilege.
- [ ] Passwords and secrets are injected securely.
- [ ] Certificate ownership and expiry monitoring are documented.
- [ ] Renewal and rotation have been tested.
- [ ] mTLS client identity is mapped to authorization policy.
- [ ] Failure behavior is observable without leaking sensitive data.
- [ ] A compromise and emergency rotation runbook exists.
- [ ] Test keys are not reused in production.
- [ ] No private keys, P12/PFX/JKS files, or passwords are committed to source control.

## 8. Monitoring ideas

Monitor and alert on:
- Certificate expiry thresholds (for example, 30/14/7 days, adjusted to your renewal process).
- Failed TLS handshakes by service and error category.
- Truststore or keystore load failures after deployment.
- mTLS authentication failures and unexpected client identities.
- Sudden changes in certificate issuer/fingerprint where policy requires it.
- Downstream availability and TLS errors separately from HTTP application errors.

Avoid recording private key material, passwords, or complete sensitive payloads.
