# Chapter 20 — Keystore, Truststore, TLS, and Mutual TLS in Mule 4

## Why this chapter matters

Mule applications routinely call HTTPS APIs, expose HTTPS listeners, connect to databases and message brokers over TLS, and sometimes authenticate the other party with client certificates. To configure these connections safely, you need to understand certificates, private keys, keystores, truststores, certificate chains, TLS handshakes, hostname verification, rotation, and troubleshooting.

This chapter starts from first principles, then moves through Java keytool, Anypoint Studio configuration, outbound HTTPS, inbound HTTPS, mutual TLS (mTLS), troubleshooting, operations, and a capstone.

> **Security note:** Use test certificates and non-production secrets in labs. Never commit private keys, keystore files, passwords, production certificates with private-key material, or real secrets to GitHub. The commands here are educational templates; verify options against the JDK and Mule/connector versions in your environment.

## Learning outcomes

By the end, you should be able to:
- Explain encryption, hashing, digital signatures, certificates, CA trust, TLS, and mTLS.
- Distinguish a keystore from a truststore and a private key from a public certificate.
- Understand JKS, PKCS12/P12/PFX, PEM, DER, aliases, key passwords, and store passwords.
- Create a local test CA, server certificate, and client certificate with Java keytool.
- Configure a Mule HTTPS Listener for inbound TLS.
- Configure an HTTP Requester to trust a remote server certificate.
- Explain and design mTLS in both directions.
- Diagnose PKIX path-building errors, hostname mismatch, expired certificates, missing intermediates, wrong passwords, and protocol/cipher problems.
- Plan secure storage, access control, renewal, rotation, monitoring, and incident response.

## Architecture overview

~~~mermaid
flowchart LR
    C[Client] -->|HTTPS: TLS handshake| L[Mule HTTPS Listener]
    L --> F[Mule flow]
    F -->|HTTPS: TLS handshake| R[Remote HTTPS API]
    L -. server identity from .-> KS[Listener keystore]
    C -. verifies server using .-> CT[Client truststore]
    F -. verifies remote server using .-> RT[Mule requester truststore]
    R -. optional client certificate request .-> F
~~~

The diagram shows two separate TLS connections: inbound client-to-Mule and outbound Mule-to-remote-service. Their certificate settings are independent.

## Important principles

- **A keystore usually holds identity material**: a private key and its associated certificate chain.
- **A truststore usually holds trust anchors**: certificates of CAs or peers your application is willing to trust.
- A truststore does not prove that a server is the right hostname; hostname verification is a separate check.
- TLS encryption does not automatically mean the remote party is trusted or authorized.
- mTLS adds client-certificate authentication to the TLS handshake; application-level authorization is still required.
- Never fix a certificate error by blindly disabling certificate or hostname verification.
