# 20.2 — Keystore vs Truststore, Formats, Aliases, and Passwords

## 1. Keystore

A keystore is a container supported by Java security providers. In a TLS identity configuration, it commonly stores:
- A **PrivateKeyEntry**: private key plus associated certificate chain.
- One or more certificates in a **trusted certificate entry**, depending on format and tooling.

For a Mule HTTPS Listener, the keystore commonly supplies the server private key and certificate chain. For a Mule HTTP Requester using a client certificate for mTLS, a keystore supplies Mule's client identity.

## 2. Truststore

A truststore is a store of certificates accepted as trust anchors or trusted peers. It commonly contains:
- Root CA certificates.
- Intermediate CA certificates when explicitly used as trust anchors by the chosen configuration.
- A self-signed server certificate for a controlled lab or a carefully managed pinned-peer setup.

A truststore should contain only certificates you intend to trust. Importing a certificate is a security decision, not just a troubleshooting step.

## 3. Comparison table

| Question | Keystore | Truststore |
|---|---|---|
| Main purpose | Prove the local application's identity | Decide which certificate issuers/peers to trust |
| Typical contents | Private key + certificate chain | Public CA/peer certificates |
| Secret material? | Yes, if it contains a private key | Usually public certificates only |
| Mule inbound HTTPS | Server identity | May also need truststore if client certificates are required |
| Mule outbound HTTPS | Client identity for mTLS, if requested | Trust remote server's chain |
| Typical property names | key-store / keystore | trust-store / truststore |

Terminology can vary across Java APIs and connector configuration. The role matters more than the filename.

## 4. JKS, PKCS12, PEM, DER

- **JKS**: Java KeyStore format. Historically common in Java applications.
- **PKCS12 (.p12/.pfx)**: standard container format that can hold private keys and certificates; often a good interoperability choice when supported.
- **PEM**: Base64-encoded textual representation with BEGIN/END markers. A PEM file may contain a certificate, private key, or chain; the extension alone does not prove its contents.
- **DER**: binary encoding of an ASN.1 structure, often a certificate.
- **CRT/CER**: filename extensions that may contain PEM or DER certificates; inspect the content/encoding rather than guessing.

A truststore may be JKS or PKCS12. Mule and Java versions support different combinations, so explicitly configure the store type and check the current runtime documentation.

## 5. Aliases and passwords

- **Alias**: name used to locate an entry inside a keystore.
- **Store password**: protects access to the store as a whole, subject to format/provider behavior.
- **Key password**: may separately protect the private key entry.
- **Certificate password**: certificates themselves are public; “certificate password” often informally refers to the store/key password.

For interoperability, many workflows use the same store and key password, but don't assume that requirement without checking your Java provider and Mule version. An incorrect alias can cause the wrong identity to be selected or no private key to be found.

## 6. Common layout

~~~text
local-tls-lab/                 # outside the Git repository
  root-ca.p12                  # CA private key: protect carefully
  server-identity.p12          # server private key + chain
  server-truststore.p12        # CA/public trust certificates
  client-identity.p12          # client private key + chain
  client-truststore.p12        # CA/public trust certificates
  exports/
    root-ca.cer
    server.cer
    client.cer
~~~

In a production deployment, CA private keys should be managed under stricter controls than app identities; often they should not be present on application hosts at all.

## 8. Safe storage rules

- Never commit `.jks`, `.p12`, `.pfx`, private-key PEM files, or passwords to a public repository.
- A public CA certificate can usually be distributed, but document its source and intended trust scope.
- Store passwords in a secrets manager or protected deployment properties, not source code.
- Restrict filesystem permissions and access to deployment artifacts.
- Avoid copying production private keys to developer laptops.
- Have a documented rotation and revocation process.
