# 20.4 — Configure an Inbound HTTPS Listener in Mule 4

## Goal

Expose a simple Mule endpoint over HTTPS so the client validates Mule's certificate before sending an HTTP request. This is **server-authenticated TLS**, not mTLS yet.

## Flow architecture

~~~mermaid
sequenceDiagram
    participant Client as curl / Postman
    participant TLS as TLS handshake
    participant Mule as Mule HTTPS Listener
    Client->>TLS: Connect to localhost:8443
    TLS->>Client: Server certificate chain
    Client->>Client: Validate trust + SAN/hostname + validity
    Client->>Mule: Encrypted GET /secure/hello
    Mule-->>Client: HTTP 200 + JSON
~~~

## 1. Prepare a test identity

Complete the keytool steps in 20.3 to create `mule-server.p12` with alias `mule-server`, and create a truststore containing its public certificate. Keep the files and passwords outside source control.

## 2. Create the Mule project

1. Open Anypoint Studio and create a Mule 4 project.
2. Add an HTTP Listener global configuration.
3. Set the listener protocol to HTTPS (the UI differs by connector/Studio version).
4. Configure a TLS context and its key store:
   - Path to `mule-server.p12`.
   - Store type: PKCS12, if supported by the chosen runtime/connector.
   - Alias: `mule-server`, if the UI exposes an alias selector.
   - Store/key password via protected configuration or a secure local lab mechanism.
5. Set a local port such as 8443.
6. Add a Listener path `/secure/hello` and method GET.
7. Add Transform Message to return a small JSON body.

Example payload script:

~~~dataweave
%dw 2.0
output application/json
---
{
  message: "HTTPS is working",
  transport: "TLS",
  authenticatedClientCertificate: false
}
~~~

This message describes the lab configuration only. The endpoint has not authenticated the client with a certificate.

## 3. Conceptual XML structure

Use Studio's generated namespaces and schema-compatible fields for your Mule/HTTP Connector version. This is a **configuration outline**, not a complete copy-paste application:

~~~xml
<tls:context name="Mule_Server_TLS_Context">
    <tls:key-store
        path="${secure::tls.keystore.path}"
        type="pkcs12"
        alias="mule-server"
        password="${secure::tls.keystore.password}"
        keyPassword="${secure::tls.key.password}"/>
</tls:context>

<http:listener-config name="HTTPS_Listener_config">
    <http:listener-connection
        host="0.0.0.0"
        port="8443"
        protocol="HTTPS"
        tlsContext="Mule_Server_TLS_Context"/>
</http:listener-config>
~~~

Exact element names and attributes can vary by HTTP Connector version. Use the Studio configuration editor and current Mule TLS docs as the source of truth. The `secure::` notation requires the corresponding secure configuration setup; it is not automatically available in every project.

## 4. Test it

When the client trusts the lab certificate and calls the hostname present in SAN:

~~~bash
curl --cacert mule-server.cer \
  "https://localhost:8443/secure/hello"
~~~

Because the lab certificate is self-signed, curl can trust the exported certificate explicitly with `--cacert`. Do not use `-k` or `--insecure` as the normal solution; it disables certificate verification and hides the trust problem.

If the exported certificate lacks SAN for localhost, generate a corrected lab certificate rather than disabling hostname verification.

## 5. What happens when a client connects?

- Mule presents the certificate chain associated with its private key.
- The client validates chain trust, validity, certificate usages, and hostname.
- TLS negotiates session keys.
- HTTP request/response data is encrypted in transit.
- The Listener flow then processes the HTTP request.

## 6. What this configuration does not do

- It does not require a client certificate.
- It does not authorize callers.
- It does not automatically make the endpoint publicly trusted.
- It does not encrypt data at rest.
- It does not remove the need for API authentication/authorization and network controls.

## Troubleshooting checklist

- Is the app actually listening on 8443?
- Does the TLS context point to the correct store?
- Does the alias contain a private key entry?
- Are the store and key passwords correct?
- Does the certificate SAN match the URL hostname?
- Is the client using the right truststore/certificate?
- Is the certificate within its validity dates?
- Are the listener protocol and port consistent?
